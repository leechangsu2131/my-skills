# 작업자 안내 (모든 AI·사람 작업자 공용)

이 저장소는 초등 교사가 쓰는 자동화 스킬 모음입니다. 여러 AI(Codex, Antigravity, Claude, bizcoder 등)와 사람이 나눠서 돕습니다.
이 문서는 **어떤 일을 맡든** 지켜야 할 공통 규칙입니다. 한 가지 일만 하려고 만든 문서가 아니니, 다른 일을 받아도 이 규칙대로 하면 됩니다.

- 저장소: https://github.com/leechangsu2131/my-skills (공개 저장소)
- 파일 원문 주소: `https://raw.githubusercontent.com/leechangsu2131/my-skills/main/<경로>`
- 할 일 목록: [docs/TASKS.md](TASKS.md)
- **지금 집중: 수업 비서 묶음만 고친다** — 묶음 스킬은 [TASKS.md 맨 위 ★](TASKS.md). 묶음 밖 스킬은 고치지 않고 그 스킬 `ISSUES.md` 에 한 줄만(교사 결정 2026-11-26, 잘 안 쓰는 스킬을 고치느라 시간이 감)
- 기본 규칙 원본: [README.md](../README.md), [CONTRIBUTING.md](../CONTRIBUTING.md), [CLAUDE.md](../CLAUDE.md)

## 1. 시작할 때 읽을 것 (순서대로, 필요한 만큼만)

1. 이 문서
2. `README.md` (저장소 구조), `CONTRIBUTING.md` (작업 규칙)
3. 맡은 스킬 폴더의 `SKILL.md` → `ISSUES.md` → 필요하면 `README.md`·`WORKLOG.md`
4. 다른 스킬 폴더는 필요할 때만 엽니다. 큰 파일은 통째로 읽지 말고 필요한 부분만 찾아 읽습니다.

## 2. 일 고르기

- 교사가 따로 시킨 일이 있으면 그것이 먼저입니다.
- 없으면 `docs/TASKS.md`에서 **내 능력 등급에 맞고 상태가 `열림`인 일**을 하나 고릅니다.
  - **R** 저장소에 브랜치·PR 을 올릴 수 있음 (Codex, Claude Code 웹, Antigravity, bizcoder, Gemini CLI 등)
  - **P** 교사 PC 에서만 할 수 있음 (비밀값·지도서 PDF·Supabase·사이트 로그인 필요) — 교사 PC 에서 도는 작업자(Antigravity·bizcoder·로컬 Claude Code·Gemini CLI)만
  - 글만 만드는 도구(ChatGPT 웹 등, 저장소에 못 씀)에는 2026-11-26 부터 일을 맡기지 않습니다.
- 고른 일은 브랜치 이름(아래)으로 표시됩니다. 고르기 전에 `git fetch` 하고, 같은 번호의 원격 브랜치(`task/<번호>-…`)가 이미 있으면 다른 일을 고릅니다.
  - **잡는 도구(R 등급은 이것으로)**: `python tools/claim_task.py <번호> <짧은-영어-설명> --name <내 이름>` — 받아 오기(fetch)부터 같은 번호 원격·로컬 브랜치, TASKS 상태(완료·결정 대기) 확인, 브랜치 만들기·일지 '시작' 줄 올리기까지 한 번에. ❌ 가 나오면 그 일은 하지 않습니다. 확인만 할 때는 `--check`, 스킬마다 따로 잡는 일(T31·T33·S1 등)은 `--skill <스킬>`.
  - 손으로 볼 때: `git fetch --prune` 뒤 `git branch -r --list "origin/task/<번호>-*"` — 한 줄이라도 나오면 이미 누가 잡은 일입니다(설명 부분이 달라도 같은 일). 2026-11-26 같은 번호를 두 작업자가 잡아 시간이 버려졌습니다. T31·T33 처럼 여러 스킬에 걸친 일은 `task/T31-<스킬>` 처럼 스킬 이름까지 같은지 봅니다.
- **실행 직전에 한 번 더 확인합니다.** 교사에게 "이 일 할까요?" 묻고 "해"라는 답을 받았거나, 일지의 `막힘`·`그만둠`에서 이어받을 때도, 브랜치를 만들기 **바로 전에** 다시 확인합니다 — `tools/claim_task.py` 로 잡으면 이 확인이 저절로 됩니다. 교사는 여러 작업자에게 같은 일을 "해"라고 할 수 있습니다(누가 잡았는지 교사도 모를 수 있음). 이미 누가 잡았으면 시작하지 말고 교사에게 "T<번호> 는 이미 <작업자>가 하는 중이라 <다른 일>을 하겠다"고 한 줄 알린 뒤 다른 일을 고릅니다.
  - **로컬 IDE(Codex·Antigravity)는 교사 PC 의 원래 `my-skills` 폴더에서 한 번에 하나만** 일합니다(교대로). 시작·중간·끝에 `python tools/sync_work.py start <브랜치>` / `save` / `end` 로 받고 합치고 올립니다(아래 2-2). bizcoder 도 원래 `my-skills` 폴더에서 이들과 교대로 일합니다(교사 결정 2026-11-27, `tools/start_worker.ps1` 로 켬 — 일 하나 끝날 때마다 `sync_work.py end`). 그 밖의 까만 창 CLI 작업자(로컬 Claude Code·Gemini CLI)는 `tools/start_worker.ps1` 이 만든 자기 폴더(`my-skills-<이름>`)에서만 — 따로 받은 저장소·다른 폴더에서 일하면 남이 잡은 일을 못 봅니다(2026-11-25~26 T10·T11·T23·T25 가 두 번씩 만들어짐).
  - `claim_task.py` 가 푸시를 못 하는 곳(인터넷이 막힌 웹 Codex 등)에서는 교사가 준 '이번 일'만 합니다 — 교사 PC 가 그 일을 미리 잡아 둡니다. 스스로 일을 고르지 않습니다.
- 일을 하다 다른 문제를 발견하면 고치지 말고 그 스킬 `ISSUES.md` 에 적습니다. 범위를 넓히지 않습니다.

### 2-1. 할 수 있는 데까지 이어서 일하기 (R 등급)

교사가 일을 하나씩 다시 시키지 않아도 되게(교사 요청 2026-11-27): 작업자는 **도구가 고른 일을 할 수 있는 데까지** 하고, 토큰이 끊겨 멈추면 **다음 작업자가 그 브랜치를 이어받습니다**.

1. **잡기**: `python tools/claim_task.py --next --name <내 이름>` (교사 PC 작업자는 `--grade P`). 도구가 ① 내가 하던 일 ② **다른 작업자가 멈춘 일(이어받기)** ③ TASKS 의 '열림' 일(TASKS 의 `고르는 순서(claim_task.py --next)` 줄 순서) 차례로 골라 잡습니다. 새 일이면 브랜치 `task/<번호>-…` 와 일지 `시작` 줄을, 이어받기면 그 브랜치에 내 `이어받음` 줄을 **바로 푸시**합니다. 한 일에 브랜치는 하나만.
2. **하기 — 언제 끊겨도 되게**: 작은 단계(30분 안쪽)마다 커밋·푸시하고 일지에 `진행 — 한 것 / 다음: 할 것` 한 줄. 이어받는 작업자는 이 줄과 TASKS 의 체크리스트를 보고 이어 갑니다.
3. **올리기**: 쓸 만한 중간 단계(시험 통과)면 일지 `합칠 준비` → PR 하고 같은 브랜치에서 계속(교사 PC 가 그때그때 합침). 일 전체가 끝나면 `PR 올림` → PR.
4. **다음 일**: 기다리지 말고 1번(`--next`). 고를 일이 없다고 하면 `docs/TASKS.md` 맨 아래 **"상시 일(S)"** 을 `--skill` 로 잡습니다.
5. **막히면** 일지에 `막힘`(이유·필요한 것)을 적고 브랜치를 그대로 둔 채 다음 일로. 교사 PC 가 보고 풉니다(막힘은 이어받지 않음).
6. **그만둘 때**(사용량 끝 등) 일지에 `그만둠`(어디까지, 다음에 할 것)을 푸시합니다 — 그러면 다음 작업자가 2시간을 기다리지 않고 바로 이어받습니다. 못 적고 끊겨도 마지막 `진행` 줄이 있으면 2시간 뒤 이어받힙니다.
- **이어받는 기준**: 마지막 일지 줄이 `그만둠` 이면 바로, `시작`·`진행`·`합칠 준비`·`이어받음` 인데 **2시간 넘게 새 커밋이 없으면**. `PR 올림`·`막힘` 은 이어받지 않음. 둘이 같은 때 이어받으면 늦은 쪽은 푸시가 거절돼 ❌(다른 일로). 아직 2시간이 안 됐는데 실제로 일하는 중이면 30분마다 푸시하는 규칙 때문에 겹치지 않습니다.
- 일지 쓰는 법: [worklog/README.md](worklog/README.md). 내 이름은 교사가 정해 줍니다(예: `bizcoder-2`). 다른 작업자 일지는 고치지 않습니다.

### 2-2. 큰 프로젝트 하는 법 (Codex·Antigravity) — 합칠 때 덜 꼬이게

맡은 프로젝트는 [TASKS.md 의 '★ 큰 프로젝트' 표](TASKS.md)에 있습니다(번호 P1, P2 …, 맡은 이, 영역 파일).
1. **로컬 IDE 는 한 번에 하나, 브랜치는 프로젝트마다 하나**: 교사 PC 의 원래 `my-skills` 폴더에서 Codex·Antigravity 가 교대로 일합니다. 둘을 동시에 켜지 않습니다(한 폴더는 한 번에 한 브랜치라 서로의 파일이 바뀜). 브랜치는 `proj/P<번호>-<짧은-영어>`(이미 `task/…` 로 시작했으면 그대로). 클라우드 Codex 는 GitHub 에서 따로 일하므로 같이 돌려도 됩니다.
2. **자주 올리고 자주 합친다**: 쓸 만한 한 단계(시험 통과)가 되면 바로 푸시하고 일지에 `합칠 준비 — 무엇이 되었나, 시험 결과`. 교사 PC 의 Claude Code 가 그때그때 main 에 합칩니다. 며칠치를 한꺼번에 쥐고 있으면 충돌이 커집니다. 합쳐진 뒤에도 같은 브랜치로 이어서 일하면 됩니다.
3. **받고 올리기는 명령 하나로, 자주** (로컬에서 일하므로 안 올리면 아무도 못 봄 — GitHub 에서 일하는 작업자와 꼬이지 않게):

   | 언제 | 할 것 |
   |---|---|
   | 일을 시작할 때(IDE 를 켜거나 대화를 새로 열 때) | `python tools/sync_work.py start <내 브랜치>` — 앞 IDE 가 남긴 변경이 있으면 멈춤, 최신 main 까지 받음 |
   | 한 단계가 끝날 때(시험 통과)·1~2시간마다 | 고친 파일만 `git add` → `git commit` → 일지 `합칠 준비`(또는 `진행 — 어디까지`)도 커밋 → `python tools/sync_work.py save`(최신 main 합치기 + 올리기) |
   | 교사가 "합쳤다"고 할 때 | `python tools/sync_work.py save` |
   | 끝낼 때(다른 IDE 로 바꾸기 전·창을 닫기 전) | 커밋 → 일지 `그만둠 — 어디까지, 다음에 할 것` 커밋 → `python tools/sync_work.py end`(올리고 폴더를 빈 상태로 → 다음 IDE 가 바로 시작). **커밋 안 한 변경을 남기고 끝내지 않는다** |

   - 도구는 rebase·`--force` 를 쓰지 않습니다(merge). 충돌이 나면 합치기를 취소하고 충돌 파일을 알려 줍니다 → 내 영역 파일이면 `git merge origin/main` 으로 다시 합쳐 직접 풀고, 남의 영역이면 일지에 `막힘`.
   - `⚠ 같은 파일을 고치는 다른 브랜치` 가 나오면 교사(Claude Code)에게 알려 먼저 합칠 쪽을 정합니다.
   - 도구를 못 쓰면 같은 순서를 손으로: `git fetch origin` → `git merge origin/main` → `git push -u origin <브랜치>`.
4. **큰 공용 파일은 덜 고친다**: `web/index.html`·`assistant_server.py` 처럼 여럿이 고치는 파일에는 불러오는 몇 줄만 넣고, 새 기능은 새 파일(`web/<기능>.js`·`.css`, `<기능>_api.py` 등)로 만듭니다. 영역 밖 파일을 고쳐야 하면 일지와 PR 설명에 적습니다.
5. **번호 붙는 기록은 합칠 때**: `ISSUES.md` 새 항목은 `ISSUE-새: 제목` 으로 쓰면 합칠 때 번호를 붙입니다. `docs/TASKS.md` 는 고치지 않습니다(Claude Code 가 함).
6. **막히면**: 일지에 `막힘 — 무엇이, 해 본 것, 필요한 것` 을 푸시하고 교사에게 한 줄. Claude Code 는 작업자 브랜치에 직접 커밋하지 않고(작업자 폴더와 엉킴) 고칠 내용을 알려 주거나 `help/P<번호>-…` 브랜치로 줍니다.
7. **흡수한 T 번호**는 따로 잡지 않아도 됩니다(TASKS 상태가 `프로젝트 P<n>` 이면 다른 작업자는 못 잡음). 프로젝트 밖 T 번호 일을 하고 싶으면 평소처럼 `claim_task.py` 로 잡습니다.

## 3. 원칙과 꼭 지킬 것

**원칙**: 이 프로젝트에서 중요한 것은 **기능, 효율, 노하우 쌓기**입니다. 규칙은 최소로 둡니다. 막는 것은 **법적·금전적 문제나 실제 피해가 생길 수 있는 것**뿐입니다(교사 결정, 2026-11-25. 수익이 생기면 다시 정함).

꼭 지킬 것 (이것만):
- **학생·학부모 개인정보**(이름·학번·평가 글·사진·녹음)를 저장소·공개 외부 서비스에 올리지 않습니다 — 학교가 법적으로 지켜야 하는 정보. 시험 예시는 `학생A` 처럼. 학생 기록·결과물은 `data_dir()`(교사 PC 의 내 문서\my-skills-data) 에만 둡니다(단, 교사가 직접 요청한 본인 개인 Google Drive·시트 업로드는 허용, 2026-11-27 교사 결정).
- **누구든 전화번호·집 주소**를 쓰지 않습니다 — 공개되면 스팸·사칭 같은 실제 피해가 생김. 예시는 `000-0000`.
- **비밀값**(API 키·토큰·비밀번호)을 코드·문서·커밋에 쓰지 않습니다 — 새면 돈이 나감. 비밀값은 교사 PC 의 중앙 `.env` 한 곳에만, 코드는 `skills/_shared/skill_env.py` 로 읽고, 필요한 시험은 가짜(mock)로.
- **저작물**(지도서·교과서 PDF 등)을 저장소에 올리지 않습니다.
- **바깥에 실제로 영향을 주는 실행**(NEIS·에듀파인 제출, 문자 발송, 결제·구매, 삭제)은 작업자 일에서는 하지 않습니다. 교사 PC 에서 교사가 대화로 직접 시킨 **비서 일**은 그 스킬대로 진행하고, 되돌릴 수 없는 마지막 단추(승인요청·상신·발송·결제) 바로 전에 한 번 확인받아 누릅니다(교사 결정 2026-11-27).

괜찮은 것: 작업자 이름(실명·별명 모두), 교사·교직원 이름, 이메일 주소, 학교 업무 정보 — 위 다섯 가지가 아니면 막지 않습니다.
기술 습관(규칙이 아니라 잘 돌게 하려는 것): 절대 경로(`C:\Users\<이름>\…`) 대신 `%OneDrive%`·`%USERPROFILE%`·`data_dir()` — 다른 PC 에서도 돌게.

## 4. 올리는 방법 (R 등급)

- `main` 에 바로 올리지 않습니다. **브랜치 + PR** 로 올리고, 합치기는 교사 PC 의 Claude Code 가 검토 뒤에 합니다.
- 브랜치 이름: `task/<TASKS 번호>-<짧은-영어-설명>` (예: `task/T12-tests-library-search`). 목록에 없는 일은 `feature/…`, `fix/…`, `docs/…`.
- 고친 파일만 골라 `git add <파일>` 합니다(`git add -A` 금지).
- 커밋 전: `git diff --staged` 로 학생 정보·전화번호·비밀값이 없는지 보고, `python tools/build_catalog.py --check` 통과를 확인합니다. 시험이 있으면 돌립니다.
- 커밋 메시지: `feat: [스킬명] 설명` / `fix:` / `docs:` / `test:` / `refactor:` (한국어 설명 가능)
- PR 설명에 적을 것: 무엇을 했나, 어떻게 확인했나(시험 결과), **교사 PC 에서 따로 할 일**(키 연결·실제 실행 등), 못 한 것.
- `CATALOG.md` 는 직접 고치지 않습니다(`python tools/build_catalog.py` 로 생성).

## 6. 글쓰기 규칙

- 문서와 설명은 **쉬운 한국어**. 기술 용어는 꼭 필요할 때만, 처음 나올 때 짧게 풀어 씁니다.
- 스킬 문서 양식: `docs/templates/SKILL.md`, `docs/templates/ISSUES.md` (ISSUES 는 🔵 진행 중 / 📌 백로그 / 🟢 해결됨, `ISSUE-번호: 제목 (날짜)`).
- 문제를 해결하거나 막히면 그 스킬 `ISSUES.md` 에 증상·원인·해결·관련 파일을 남깁니다(새 기록 파일을 만들지 않음).

## 7. 작업자 프로젝트에 넣을 지침 문구

각 AI 의 '프로젝트 지침' 칸에 넣을 글(전체본·짧은본·넣는 곳)은 **[WORKER_INSTRUCTIONS.md](WORKER_INSTRUCTIONS.md)** 에 있다. 바꿀 곳은 작업자 이름 한 군데뿐. 지침 글을 고칠 때는 그 파일 하나만 고친다.

## 8. 끝나면

- R: PR 을 올리고, `docs/TASKS.md` 는 고치지 않습니다(상태 표시는 합칠 때 교사 PC 에서 함). PR 설명 첫 줄에 TASKS 번호.
- 시간이 남으면 `docs/TASKS.md` 에서 다음 일을 고르거나, 교사가 준 다른 일을 같은 규칙으로 합니다.
