# 지비톡 쪽지 보관 작업 인계

> **최신 재개 기준:** 아래 `2026-10-23 키보드 원문 캡처 재개 상태`를 우선한다. 그보다 앞선 창 식별/수동 입력 단계는 당시 기록이며 현재 절차가 아니다. 캡처 매크로는 지비톡을 전경으로 사용하므로, 사용자가 컴퓨터를 비워 둔 동안에는 UI 입력을 실행하지 않는다.

> 반복 가능한 UI 매크로 설계 원칙은 [`references/keyboard-macro-methodology.md`](references/keyboard-macro-methodology.md)에 모았다. 현재 캡처 구현에서 확인된 복구 사례도 함께 반영했다.

## 다음 작업의 목표

지비톡 쪽지관리함의 지정 기간(우선 2026년 10월) 쪽지를 빠짐없이 로컬 Markdown으로 보관한다. 중간에 오류나 실수가 생기면 즉시 멈추고, 다음 실행에서 마지막 저장 지점을 확인해 안전하게 이어간다. 메시지 발송이나 답장 기능은 현재 범위가 아니다.

## 사용자의 작업 방식 선호

- 사용자는 평소 다른 일을 할 수 있도록 키보드 중심의 반복 입력/단축키 매크로를 원한다.
- 자동으로 여러 쪽지를 넘길 때 일정한 입력 간격을 두고, 이상 징후가 있으면 멈추기를 원한다.
- 백그라운드 대상 키 입력이 실제 지비톡에서 동작하는지는 아직 검증되지 않았다. 지비톡을 사용자 대신 직접 조작할 수 있다고 가정하지 말 것.
- 사용자가 PowerShell에서 수동으로 한 건씩 날짜·발신자 입력을 하도록 부담을 넘기기보다, 현재 세션/앱 상태와 자동화 가능한 범위를 먼저 확인하고 에이전트가 구현·검증할 수 있는 부분을 진행할 것.

## 현재 코드와 보관 상태

- 작업 폴더: `skills/admin-gbetalk`
- 주요 코드: `gbtalk_summary.py`
- 안내: `README.md`
- 기존 월별 보관: `inbox/2026-10.md`
- 보관 파일에는 22개 제목 행이 확인됐고, 날짜 범위는 2026-10-19 09:49부터 2026-10-22 11:20까지다. 본문은 실제로 전부 완전한지 검증되지 않았다.
- `inbox/.sessions` 체크포인트 폴더는 직전 확인 시 없었다. 기존 파일에서 가장 오래된 기록(2026-10-19 09:49)을 새 세션의 재개 기준으로 추정하도록 코드를 변경했다.
- 우선 대상 기간은 2026-10-01부터 2026-10-31까지로 이해한다. `--before 2026-10-01`은 10월 1일보다 오래된 첫 항목을 만나면 완료로 처리하는 설정이다.
- 직전 변경에서 날짜 형식 오류, 복사 미확인, 빈 클립보드, 보관 파일 쓰기 오류 때 체크포인트에 사유를 남기고 중단한다. 완료된 기간은 재실행 시 자동 수집하지 않는다.
- `python -m py_compile skills/admin-gbetalk/gbtalk_summary.py`와 `git diff --check`는 통과했다. 실제 GBTalk에서 실행한 검증은 아니다.

## 알려진 위험 및 미검증 사항

- 목록의 `End` 키가 여러 쪽지를 건너뛴 적이 있다. 현재 키보드 포커스/이동 경로는 신뢰할 수 있다고 보장할 수 없다.
- 과거 확인에서 GBTalk는 설치형 프로그램(`AtMessengerMobileEdition.exe`)이었고, 쪽지관리함은 별도 창으로 열렸다. 본문 텍스트는 일부 UIA에서 읽혔지만, 시각·발신자 등의 필드 구조와 전체 목록 순회는 확정되지 않았다.
- 기존 아카이브의 제목 행 수와 실제 누락 여부는 완전성 증거가 아니다. 날짜 구간에 공백이 있는지 원본 목록과 대조해야 한다.
- `archive-session`은 여전히 사람이 날짜/발신자를 입력하는 보조 모드다. 별도 `capture_macro.mjs`는 쪽지관리함에서 키보드로 이동하며 원문 UIA 값을 30건 이하로 임시 수집한다. 대상 창 입력은 전경을 활성화하므로 백그라운드 동작은 보장되지 않는다.

## 다음 작업에서 이어갈 순서

1. 이 문서와 `README.md`, `gbtalk_summary.py`, `inbox/2026-10.md`를 확인하고 사용자가 앞서 설명한 의도를 재질문하지 않는다.
2. 현재 지비톡/컴퓨터 사용 상태를 먼저 확인한다. 사용자가 다른 일을 하고 있을 수 있으니 포커스를 바꾸거나 키를 보내기 전에 앱 상태를 살핀다.
3. 코드 체크포인트 로직을 검토한다. 특히 저장 직후 프로세스가 비정상 종료된 경우와 중복 확인 후 재개하는 경우를 살펴보고, 마지막 저장 위치가 잘못 전진하지 않는지 확인한다.
4. 수동 실행을 사용자에게 요구하기 전에, 현재 제공된 컴퓨터 제어 기능으로 읽기 전용 관찰 및 짧은 테스트를 에이전트가 수행할 수 있는지 판단한다. 테스트는 사용자 작업을 방해하지 않도록 소수 항목만 대상으로 하고, 오류/날짜 역행/같은 본문 반복이면 중단한다.
5. UI 요소에 직접 키를 보내는 방식이 가능하면, 실제 쪽지 목록에서 한 항목씩 이동하고 매번 날짜·발신자·본문 변경을 검증하는 프로토타입을 만든다. 검증 실패 시 자동 저장하지 말고 체크포인트에 오류 지점을 남긴다.
6. 자동화 중 사용자 PC를 계속 사용할 수 있는지 별도로 확인한다. 백그라운드 타깃 입력이 불안정하면 활성 창 매크로가 다른 작업을 방해할 수 있음을 분명히 알리고, 이를 확인 없이 ‘동시 작업 가능’이라고 하지 않는다.
7. 작은 구간에서 복구까지 확인한 다음 10월 전체 수집으로 확장한다. 전송/답장 기능은 추가하지 않는다.

## 2026-10-22 이어서 진행한 내용

- 체크포인트에 보관 전 쓰기 의도(파일, 오프셋, 블록 크기/해시)를 먼저 기록하도록 `gbtalk_summary.py`를 보완했다.
- 쓰기 전 기존 파일 앞부분의 크기와 SHA-256도 기록하고, 재실행 때 앞부분과 추가 블록을 모두 검증하도록 보강했다. 기존 앞부분이 달라졌거나 일부 기록이면 파일을 수정하지 않고 중단한다.
- 임시 디렉터리에서 기록 전 종료, 기록 후 종료, 부분 기록, 같은 크기의 기존 앞부분 변경을 검증했다. 네 경우 모두 예상대로 통과했고, 거부된 두 경우에서 파일 바이트가 보존됨을 확인했다.
- README에 앞부분/블록 해시 검증을 설명했다. `python -m py_compile`도 통과했다.
- 지비톡 창 목록을 다시 읽기 전용으로 확인했다. `받은 쪽지읽기` 제목 창 5개가 있어 대상을 특정하지 못했고, 포커스 이동/키 입력은 하지 않았다.
- 사용자의 설명에 따라 개별 `받은 쪽지읽기` 창을 구분하지 않고, 주 메신저의 `쪽지` → `쪽지관리함` 경로로 관리함을 열었다. 이 경로로 만든 `쪽지관리함` 창은 제목 기준 유일하게 식별됐다.
- 관리함 화면에는 수신 쪽지 목록이 최신순으로 보이고 발신자/미리보기/시각이 표시됐다. 읽기 전용 접근성 트리는 목록을 하나의 `수신함 리스트`로만 노출하고 행 텍스트나 전체 본문은 제공하지 않는다.
- 목록을 520 단위로 한 번 스크롤했을 때 오래된 항목으로 약 두 행 이동했고, 10-22와 10-21 항목이 보였다. 개별 쪽지는 열지 않았고 보관 파일도 변경하지 않았다. 전체 목록 탐색/본문 복사 가능성은 아직 검증되지 않았다.
- 이후 관리함에서 2026-10-22 11:20 항목을 단일 클릭해 미리보기를 확인했다. 본문 전체가 UIA `편집 Value`에 나타났고, 화면의 안읽음 수는 34로 유지됐다.
- 목록에 포커스를 둔 뒤 `Down` 한 번으로 다음 오래된 항목(화면상 11:10)을 선택했다. 시각과 본문이 11:20 항목에서 바뀌었고 별도 창은 열리지 않았다. 이 한 단계 확인에서 보관 파일에 쓰지는 않았다.
- 이 목록은 최신순이며, 현재 월별 파일의 재개 기준은 가장 오래된 저장 항목(2026-10-19 09:49)이다. 새 저장은 그 항목보다 오래된 목록 항목부터 시작해야 기존 엄격한 날짜 순서 검사를 통과한다. 키 입력은 대상 창을 활성화해 전경을 가져오므로 백그라운드 동시 작업은 보장되지 않는다.
- `민원건수 조사` 검색으로 기준 항목(10-19 09:49)을 찾고 선택할 수 있었다. 검색 탭을 닫아 전체 목록으로 돌아오자 키보드 선택 위치가 최신 항목으로 초기화됐다. 뒤이어 `Down` 한 번으로 10-22 14:30 항목이 선택되어 날짜가 기준보다 최신으로 역행했다. 역행 감지에 따라 탐색을 중단했고, 보관 파일은 변경하지 않았다. 검색 결과에서 기본 목록으로 돌아올 때 선택 위치를 안전하게 보존하거나 기준 다음 항목을 찾는 방법을 먼저 설계해야 한다.
- 다음에는 지비톡 창을 하나로 식별할 수 있는 상태에서 읽기 전용으로 접근성 트리를 확인하고, 작은 구간의 목록 이동 가능성을 검증한다. 여러 창이 계속 같은 제목이면 사용자 화면에서 대상 창을 특정할 방법을 먼저 찾고, 복구 로직은 임시 폴더 사본으로 점검한 뒤 실제 아카이브에는 적용하지 않는다.

## 실행 명령 참고

작업 폴더에서 실행하는 현재 수동 보관 명령:

```powershell
python .\gbtalk_summary.py archive-session --before 2026-10-01 --period month
```

사용자에게 이 명령 실행을 다시 요청하기 전에, 새 작업에서 실제 앱 상태를 확인하고 에이전트가 직접 진행할 수 있는 수단을 먼저 검토한다.

## 2026-10-22 실제 앱 창 목록 재확인

- Computer Use의 `list_apps()`로 읽기 전용 확인했다. 지비톡 프로세스 `AtMessengerMobileEdition.exe`가 실행 중이다.
- 동일 프로세스 아래 제목 `받은 쪽지읽기` 창 5개, 메인 창 `경북교육 업무용 메신저` 1개가 반환됐다.
- 받은 쪽지읽기 창들의 제목이 동일하고, 목록 결과에는 메시지별 발신자/시간 등 구별 정보가 노출되지 않아 대상 한 개를 고를 수 없다.
- 창 활성화, 포커스 이동, 클릭, 키 입력은 하지 않았다.
- 다음 단계: 사용자가 원하는 쪽지읽기 창 하나만 남기고 나머지 읽기 창을 닫거나, 원하는 대상임을 구분할 수 있도록 해당 쪽지읽기 창의 고유한 식별 정보(예: 고유 제목 또는 앱 안에서 구별 가능한 기준)를 마련한다. 사용자가 직접 창을 정리하면 이후 다시 목록을 확인한다.

## 우선 인계: 최신 쪽지관리함 탐색 상태 (2026-10-22, 사용자 제공 진행 보고)

### 목표와 범위

- 2026년 10월 전체 쪽지를 빠짐없이 로컬 Markdown으로 보관한다. 우선 기존 보관 기준인 `2026-10-19 09:49` 다음의 더 오래된 쪽지를 이어서 수집한다.
- 수집은 쪽지관리함의 목록/미리보기에서 진행한다. 개별 `받은 쪽지읽기` 창을 구별해서 열 필요가 없다.
- 사용자는 입력 매크로를 빠르고 키보드 중심으로 진행하길 원한다. 중간 오류나 날짜 순서 이상이 생기면 그 자리에서 정지하고 재개 위치를 남긴다.
- 사용자는 자리를 비운 약 2분 동안 가능한 한 많은 쪽지를 복사하는 것을 목표로 하며 키보드 입력을 최대화하길 원한다. 속도는 목표로 두되, 전체 항목 수·포커스 이동·복사 검증을 측정하기 전에는 2분 완료를 보장하지 않는다.
- 안전한 매크로는 `Enter`/`Space`로 버튼을 활성화하지 않고 `Delete` 키도 보내지 않는다. 포커스가 목록 행인지 확인하고, 본문이 비었거나 선택 행/본문이 갱신되지 않으면 멈춘다. 비연속 동일 본문은 별개 쪽지일 수 있어 그대로 보존한다.
- 보내기/답장은 범위 밖이다. 원문을 월별 Markdown에 저장하는 것이 우선이다.

### 지비톡을 여는 경로

1. 이미 로그인된 지비톡 메인 창 **경북교육 업무용 메신저**를 사용한다. 로그인/인증은 자동화하지 않는다.
2. 메인 창에서 **쪽지**를 연다.
3. 쪽지 목록에서 **쪽지관리함** 버튼을 눌러 관리함 창을 연다.
4. 관리함의 목록에서 항목을 선택하고 아래쪽/옆쪽 미리보기의 본문을 확인한다.
5. 예전의 `받은 쪽지읽기` 창 여러 개를 대상으로 삼지 않는다. 쪽지관리함 목록을 대상으로 한다.

### 확인된 키보드/화면 동작
