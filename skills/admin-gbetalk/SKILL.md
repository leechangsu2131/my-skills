# GBTalk note archive

Use this skill to collect received notes from the GBTalk **쪽지관리함** into local monthly Markdown. The archive is local; this workflow does not send, forward, or reply to messages.

## Collection workflow

1. Read `NEXT_STEPS.md` for the current archive boundary, read relevant entries in [references/troubleshooting.md](references/troubleshooting.md) for known failures, and read [references/keyboard-macro-methodology.md](references/keyboard-macro-methodology.md) for the reusable procedure before any UI capture or resume. Use the running GBTalk main window and open **쪽지 → 쪽지관리함**. Do not choose among same-titled individual `받은 쪽지읽기` windows.
2. Use the Computer Use skill for all Windows app interactions. Select the unique `쪽지관리함` window from the current app inventory, then explicitly select **받은쪽지함** in the left navigation and verify the header says **쪽지함 받은쪽지함**. The generic **쪽지함** list can contain sent as well as received notes.
3. For a fresh pass, focus the selected row under `UltariList` and use `Home` to select the newest row. Before `Home` or `↓`, verify both that focus is on a row beneath `UltariList` and that the screenshot's highlighted row/header/body agree with the UIA row/body. A focused UIA element alone is not enough when the screen disagrees. During discovery, follow the separate one-key probe procedure in `references/keyboard-macro-methodology.md`; do not test a new route inside a capture batch. Refresh the state after every move and wait until the row and body agree; a first response was stale once. Do not assume a selection survived search, tab closure, or other view changes.
4. Read received date and sender from the selected row/header. Do not infer received time from a forwarded message header inside the body; those timestamps can differ. Prefer an exact UIA header value; if the UIA tree does not expose the date, read the visible header with OCR after confirming the selected row/body pair is stable. Do not open another message window or move the selection just to get the date. Read the full body from its UIA value when available. Otherwise click the body edit control identified in the latest tree, verify that it has focus, then use `Ctrl+A`, `Ctrl+C` and compare the clipboard to the UIA body. To restore list focus, use only a route already observed to work in the current window state. Do not click a UIA row index merely because it was returned: a recent index-10 click selected a different visible row. After any focus action, refresh and compare the highlighted row, header, body, and UIA values before sending a navigation key.
5. Keep the loop non-destructive: never send `Delete`, `Enter`, or `Space` to an uncertain focus. `Tab` from the body reached its scrollbar and then the **삭제** button in a test; do not send a fixed Tab sequence. `capture_macro.mjs` may click a list element during preflight when focus is missing. Invoke it only after the current selected row and screen/UIA state agree and the focus-recovery route has been verified; a successful click return does not prove it selected the intended row. A repeated adjacent row/body pair is ambiguous, so stop and inspect rather than silently skipping or duplicating it. Non-adjacent identical bodies are retained as separate notes.
6. For fast raw staging, use `scripts/capture_macro.mjs` with the Computer Use `sky` client. It fingerprints the selected row and body and writes synced JSONL/checkpoint data in batches of at most 30. `Home`/`↓` are the primary navigation; it reads the body through UIA and reads the date from UIA when available, using OCR only when the date is not exposed. A move is valid only when both fingerprints change together and the same pair is observed again. If the selected row is exactly `취소된 메시지입니다.`, use that placeholder rather than a stale preview value. If its pair matches multiple baseline messages, only `captureOlderThanKnown`'s `confirmedDistinctCandidate` may allow it through after visible date/sender, every baseline match, and the adjacent saved cursor are verified; that confirmation is persisted and checked again during resume. It does not save screenshots or message attachments. New raw rows include `received_date` only; sender/title still require review, so do not pass them to `archive-batch` until metadata has been reconciled. For final monthly storage, map `received_date` and `title` in a CSV and use `scripts/build_archive_input.py` to validate the raw rows and create the Markdown archive; `gbtalk_summary.py archive-batch` expects timestamped `received_at` values.
7. Inspect each 30-note batch before starting the next: confirm sequential JSONL rows, body hashes, checkpoint prefix hash, and no adjacent row-fingerprint repeats. On restart, validate the saved prefix and inspect `next_row` and `replay_cursor` separately. A `paused-ui-sync-error` with a saved `replay_cursor` may have advanced the live selection after that cursor; do not assume the helper will safely rescan from `Home`. Continue only when the live screen/UIA pair matches the recorded cursor or a documented recovery path. If they disagree, stop UI input and record the state in `NEXT_STEPS.md` and the methodology reference before changing the recovery code. If the user needs the computer or stops UI input, continue independent offline work from the existing raw files and recorded screenshots; do not repeat verified capture rows. A two-minute unattended run remains a speed target, not a promise. Computer Use input brings the manager to the foreground, so background use is not guaranteed.
8. For an offline capture whose row metadata has already been checked in a CSV, use `scripts/build_archive_input.py <raw.jsonl> <metadata.csv> <verified.jsonl> --month YYYY-MM`. The CSV needs sequence and title; it may also provide `received_date` (date only) or `received_at` (timestamp). If both date columns are absent or a row's date is blank, the builder uses that raw row's existing `received_date`/`received_at`. It verifies a contiguous metadata prefix, each raw body hash, selected-month membership, and newest-to-oldest order. Other months in the same mapped range are filtered out after the full date order is checked. `--markdown-output <new-file.md>` can render a standalone archive and refuses to overwrite an existing Markdown file. Add `--range-manifest <file.json>` to record the verified range's newest and oldest date, sender, body preview, fingerprints, and JSONL hash. Keep a received-only snapshot separate when an older monthly archive's source scope or message bodies do not match; do not feed the entire capture into append-only `archive-batch` in that case.
9. For new mail after a trusted inbox capture, use `captureNewUntilKnown` from `scripts/capture_macro.mjs` with the trusted raw, verified JSONL, and range manifest plus a separate output folder. It starts at `Home`, saves at most 30 new rows, and stops before an exact row-plus-body fingerprint match from the baseline. Treat that match as a boundary candidate: compare the selected row's visible date/sender with the range metadata before declaring completion, since an identical message can recur. A row-only or body-only match is ambiguous and stops without saving that item. Continue only from `paused-batch-complete`; do not call the capture complete until status is `paused-existing-boundary` and the candidate metadata matches. Use a fresh output folder for a later incremental run after a boundary has already been reached.
10. To backfill before a saved range, use `captureOlderThanKnown` with the same pinned raw/verified/manifest trio and a separate output folder. The first run only locates `manifest.oldest` and returns `paused-oldest-anchor-candidate`; it writes no bodies. Compare the visible date and sender with the manifest, then rerun with `confirmedAnchor: { received_at, sender }`. If the current selection still matches the saved candidate's row/body fingerprints, continue there without scanning `Home` again; otherwise rescan and verify the anchor. For later batches, resume directly when the current selection matches the checkpoint's unique `next_row`; otherwise re-find the anchor and revalidate the saved prefix. It captures older rows in batches of at most 30 and skips unique row/body pairs already present in the raw baseline after the verified anchor. If the helper returns `paused-anchor-not-found`, check the saved count and the actual list end; do not repeat the same Home scan with a higher row limit unless the app's older-page/load-more route has been verified. Only `paused-oldest-reached` means the list end was reached. Ambiguous, missing, reordered, or baseline-overlap states stop for review.
11. After matching metadata, use `build_archive_input.py ... --prepend-to <received-only-monthly.md>` for newer entries or `--append-to <received-only-monthly.md>` for older entries. Both require strict date separation from the existing archive (same-day date-only entries cannot be ordered) and reject exact duplicates; they replace the archive atomically after validation. The builder can select a month from a range spanning several months, so make a separate verified output and merge for each month. Do not use these merge modes on an archive that mixes sent and received notes.
12. To fill dates in an existing raw capture, keep the raw JSONL read-only. Use `scripts/apply_date_backfill.py <raw.jsonl> <new-dated.jsonl>` with every applicable `--verified-metadata <metadata.jsonl>` and `--date-map <map.json>`. It validates source-file hashes, row/body fingerprints, date formats, conflicts, and complete coverage; it refuses an incomplete result and never overwrites an existing output. Keep the dated copy and its maps together. `out/date-completeness-audit-20261027.json` records the before/after counts for the 2026-10-27 backfill.
13. To add sender metadata, keep existing raw JSONL read-only and use `scripts/apply_sender_backfill.py <source.jsonl> <new-output.jsonl> --verified-metadata <metadata.jsonl> [--manual-map <map.json>]`. It joins by row hash, body hash, and message date, rejects conflicts or ambiguous matches, and marks unresolved rows `sender_capture_status: missing`. Bind manual rows to the source file SHA-256 plus sequence/date/row/body fingerprints and a visible-review status. Live capture functions require a `senderReader`; build it with `createVerifiedSenderReader(records)` from manually reviewed, fingerprint-bound entries. Treat Korean OCR as an unverified candidate: compare it with the visible sender header/list label before saving. If the selected message or search-return screen is inconsistent, stop and reobserve; never infer sender from quoted body text. See [`references/troubleshooting.md`](references/troubleshooting.md), [`references/keyboard-macro-methodology.md`](references/keyboard-macro-methodology.md), and `out/sender-backfill-20261028/sender-completeness-audit.json`.
14. To create date-partitioned sender status copies for August–October, run `scripts/build_sender_month_slices.py <october-sender-jsonl> <older-sender-jsonl> <new-output-dir> [--new-october-jsonl <live-capture.jsonl>]`. The builder verifies each body's SHA-256, required date/row fingerprints, source-local sequences, and cross-source duplicate fingerprints. It preserves sender evidence, sets missing senders to `null`/`missing`, and writes one JSONL per month plus source/output hashes and sender counts in `sender-month-slices-audit.json`. It refuses to overwrite an existing output directory. The optional live capture is ordered first within each date; because these inputs contain dates but not message times, do not claim exact time order for messages on the same date.
15. To render those verified month slices as user-readable Markdown, run `scripts/render_sender_month_markdown.py <month-slice-dir> <destination-dir>`. It validates each source hash, date, row/body fingerprint, sender count, and date order before writing `YYYY-MM.md` plus an index. Missing sender values remain explicitly marked. It refuses to overwrite any target Markdown file.

See `README.md` for commands and archive behavior, and `NEXT_STEPS.md` for current verification results and the next implementation steps.

The workflow has fragile app-specific focus and recovery behavior. Before each UI capture or resume, check the matching issue in [references/troubleshooting.md](references/troubleshooting.md) and read [references/keyboard-macro-methodology.md](references/keyboard-macro-methodology.md). When an observed failure changes the safe procedure, update the troubleshooting record and `NEXT_STEPS.md`, then reconcile the reusable procedure here so later runs do not repeat a known-bad action.

## Durable failure-learning record

When an observed failure changes the safe procedure, document both what happened and how it was recovered. In references/troubleshooting.md, capture the symptom, attempted action, observed result, confirmed cause (or explicitly unknown cause), recovery, evidence level, reusable rule, current output state, and remaining limitation. Update NEXT_STEPS.md with the current checkpoint and next safe action; update this methodology with the reusable procedure. Keep hypotheses separate from observations and never describe a manual visual comparison as a hash verification.
