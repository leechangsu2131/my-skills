# 키보드 매크로 방법론

이 문서는 UI 조작이 까다로운 데스크톱 앱에서 키보드 중심 자동화를 설계하고, 작은 단위로 검증하며, 중간 종료 뒤 안전하게 재개하기 위한 방법이다. 지비톡에서 실제로 관찰한 장애와 수정 이력은 [troubleshooting.md](troubleshooting.md)에 모은다. 아래의 앱 동작은 지비톡에만 적용하며 다른 앱이나 화면에서는 포커스와 키 경로를 다시 확인한다.

## 1. 조작 전에 범위와 창을 확인한다

- 작업이 읽기·복사만 필요한지 먼저 정의하고, 삭제·전송·답장처럼 범위 밖 동작을 구체적으로 금지한다.
- 창 목록과 접근성 트리를 읽어 대상 창을 하나로 식별한다. 같은 제목 창이 여러 개면 임의로 고르지 말고, 목록·창 내부 상태 등 안전한 구별 정보를 찾는다.
- 키 입력이 앱을 전경으로 가져오는지 확인한다. 전경 입력이면 다른 앱에서 동시에 작업할 수 있다고 가정하지 않는다.
- 첫 조작 전 화면 상태, 현재 선택, 포커스를 기록한다. 대상 앱에 입력을 보내기 전까지는 읽기 전용 관찰을 우선한다.
- 여러 범주가 섞인 목록에서는 목표 폴더를 명시적으로 선택하고 화면 제목/경로를 확인한다. 지비톡의 기본 `쪽지함`은 받은 쪽지와 보낸 쪽지가 섞일 수 있으므로 원문 백업은 `받은쪽지함`을 선택한 뒤 시작한다.

## 2. 키 경로를 한 번에 하나씩 배운다

- 현재 포커스와 접근성 컨트롤을 확인한 뒤, 결과가 명확하고 되돌릴 수 있는 키 하나만 보낸다.
- 입력 직후 UI 상태를 다시 읽고, 선택 행·헤더·본문 중 관련 값이 실제로 바뀌었는지 확인한다. 첫 응답이 오래된 상태일 수 있으므로 값이 안정될 때까지 제한된 횟수로 재관찰한다.
- 실제로 확인하지 않은 `Tab` 횟수, 단축키, 키 반복 속도는 가정하지 않는다. 특히 포커스를 모르는 상태에서 `Enter`, `Space`, `Delete`를 보내지 않는다.
- 한 단계의 전제와 결과를 기록한다. 예: “목록 행에 포커스가 있을 때 `Down` 1회 → 다음 행과 미리보기 본문이 함께 바뀜.”
- 검색·탭 전환·창 재활성화 뒤에는 이전 선택 위치가 유지된다고 가정하지 않는다. 기준 행과 현재 행을 다시 대조한다.
- 포커스 판정은 컨트롤 역할, 부모 목록과의 관계, 화면의 강조 행을 함께 확인한다. UIA 클릭의 성공 반환이나 포커스 요소 번호만으로 현재 선택을 확정하지 않는다. 지비톡 helper의 포커스 검사는 UIA 포커스 인덱스와 첫 목록 행 인덱스의 일치만 확인하므로 화면의 강조 행 내용까지 증명하지 않는다. 화면/머리글/본문과 UIA 행/본문 중 하나라도 다르면 캡처하지 않는다. 확인된 실패 경로는 [트러블슈팅 이력](troubleshooting.md)을 참조한다.
- 목록 강조, 미리보기의 날짜/발신자, UIA 본문이 서로 다른 쪽지를 가리키면 이동 키와 복사를 보내지 않는다. 창을 다시 식별하고 한 번 전경화·최대화해 화면을 복구할 수는 있지만, 오래된 요소 번호를 반복 클릭하지 않는다. 새 상태에서도 요소가 캐시되어 있지 않거나 화면 식별 정보가 없으면 중단하고 오류와 마지막 확정 순번을 기록한다.
- UI 동기화 오류 뒤 `replay_cursor`가 마지막으로 대조된 저장 행을 가리키더라도 화면은 이미 다음 행으로 이동했을 수 있다. 체크포인트 행과 화면의 현재 행이 다르면 해시만으로 다음 행을 추정하지 않는다. 복구 도중 화면/본문 불일치가 생기면 현재 커서를 무효로 보고 새 관찰부터 시작한다. 재현된 사례와 현재 해결 상태는 [트러블슈팅 이력](troubleshooting.md)에 기록한다.
- 대상 앱 프로세스가 종료되거나 창 핸들이 사라지면 이전 창 객체·요소 번호·선택 커서를 버린다. 앱 목록을 다시 읽어 창을 재발견하고, 로그인 화면이면 인증 자동화를 시도하지 않는다. 사용자가 직접 인증한 뒤 관리함을 새로 식별하고, 저장된 JSONL 접두부와 현재 행을 확인한 다음에만 이어간다. 종료 직전 `next_row`가 없거나 UI 동기화 오류가 기록됐다면 마지막 저장 행의 해시만으로 다음 목록 행을 추정하지 않는다.
- UIA에서 행·본문 지문이 서로 일치하거나 기존 JSONL 지문과 같더라도, 같은 시점 화면의 강조 행·미리보기 본문·머리글이 이를 부정하면 현재 커서로 인정하지 않는다. 유일한 대상 창을 한 번 전경화한 뒤 새 화면과 UIA를 다시 읽고, 불일치가 남으면 키 이동·복사·저장을 중단한다. 날짜 OCR 결과만으로 행/본문 불일치를 해소하지 않는다.
- 지비톡에서 선택 행 텍스트가 정확히 `취소된 메시지입니다.`이면 미리보기의 UIA 편집 값이 직전 쪽지 본문으로 남아 있을 수 있다. 이 경우 직전 본문을 취소 쪽지에 붙이지 말고, 선택 행의 취소 표식을 placeholder 본문으로 기록해 `recalled-placeholder`로 분류한다. 취소 표식이 아닌 행에서는 행·본문 지문이 모두 안정적으로 맞지 않으면 저장하지 않는다.
- 동일한 placeholder 지문이 기존 캡처 여러 곳에 나타나면 이를 자동으로 새 항목이나 중복으로 판단하지 않는다. 화면의 수신 날짜/발신자와 기준 메타데이터를 대조하고, 현재 행이 마지막 확정 커서 바로 다음임을 확인한 뒤에만 예외 데이터를 전달한다. 모호 후보는 저장 전에 기준 매치 순번과 지문을 `paused-ambiguous-existing` 체크포인트에 남긴다. 예외는 기준 매치 순번, 화면 메타데이터, 직전 저장 순번과 행/본문 지문에 묶어 raw JSONL에 저장하며, 재개 때 모두 다시 검증한다. 확인 객체가 현재 화면/커서와 맞지 않으면 Home이나 추가 키 입력 전에 중단한다.
- 동작 우선순위는 키보드, 필요한 최소 마우스, OCR 순이다. 목록의 `Home`/`↓`를 이동의 기본으로 삼고, 본문은 UIA 값으로 읽는다. 키보드만으로 원하는 값을 안전하게 가져올 수 없으면 현재 선택 행을 다시 여는 경로나 불확실한 `Tab` 순서를 만들지 않는다. 날짜는 UIA 머리글 값이 있으면 먼저 사용하고, 값이 없을 때 현재 화면의 머리글을 OCR로 읽는다. OCR은 읽기 보조일 뿐 목록 이동을 대신하지 않으며, 행·본문 지문이 안정되지 않으면 사용하지 않는다.

### 새 키 경로를 탐색할 때

키 경로 탐색은 캡처 실행과 분리한다. 검증되지 않은 키를 30건 캡처에 바로 넣지 않는다.

1. 화면 강조 행, 머리글, 본문, UIA 행/본문이 같은 쪽지를 가리키는 안정된 상태에서 시작한다. 목록 순서나 안읽음 수가 바뀌는 중이면 실험을 보류한다.
2. 되돌릴 수 있는 비파괴 키 하나만 한 번 보낸다. `Up`/`Down`부터 시험하고 `Home`은 끝점 이동인지 별도로 확인한다. `End`, 반복 키 입력, 여러 키 연속 전송은 후보에서 제외한다.
3. 즉시 새 화면과 UIA를 읽는다. 강조 행, 머리글, 본문, 포커스가 함께 예상한 한 쪽지만큼 바뀌고 동일한 상태가 두 번 연속 관찰될 때만 후보 키로 기록한다.
4. 아무것도 바뀌지 않으면 포커스 오류인지 목록 끝인지 확인하기 전까지 반복하지 않는다. 행만 바뀌거나 본문만 바뀌거나 화면과 UIA가 갈리면 실패로 기록하고 멈춘다.
5. 한 칸 이동이 확실히 확인된 경우에만 반대 방향 키 한 번으로 복귀 여부를 검증한다. 복귀가 확인되지 않으면 추가 키로 위치를 추정하지 않는다.
6. 여러 행과 날짜 경계에서 한 칸 이동이 반복 확인된 뒤에만 3건, 5건, 최대 30건으로 배치를 늘린다. 각 단계에서 순번·해시·체크포인트를 검사하고 UI 재개는 별도로 확인한다.

실험 기록에는 키와 횟수, 전후 포커스, 화면 행/머리글/본문, UIA 행/본문, 결과(한 칸 이동·무반응·혼합 상태·포커스 상실)를 남긴다. 화면 행과 미리보기가 이미 다르면 진단 키도 보내지 말고 관찰 오류로 기록한다.

## 3. 이동과 텍스트 읽기를 분리한다

- 키보드로 행을 이동하고, 본문은 UI Automation의 값처럼 구조화해 읽을 수 있는 경로를 우선 사용한다. 키보드 매크로가 반드시 클립보드 복사를 해야 하는 것은 아니다.
- UI Automation 값을 사용할 수 없을 때만 본문 컨트롤을 직접 지정해 포커스를 확인한 뒤 `Ctrl+A`, `Ctrl+C`를 시험한다. 클립보드 결과가 새로 복사된 것인지 확인하고, UIA 값과 비교한다.
- 비교 시 줄바꿈 표기처럼 확인된 형식 차이만 정규화한다. 본문 내부 공백이나 문장 내용을 무심코 합치거나 제거하지 않는다.
- 각 항목을 저장하기 전에 선택 행 식별값과 본문 해시를 만든다. 이동 후 행과 본문이 모두 안정적으로 바뀌었는지 확인한다. 같은 행 지문과 본문 해시가 이웃 항목에서 함께 반복되면 중단하고, 본문 해시만 같고 행 지문이 다르면 별개 쪽지일 수 있으므로 보존한다.
- 수신 날짜·발신자 같은 메타데이터를 본문 안의 전달 원문이나 서명에서 추정하지 않는다. 원문 캡처는 확인된 `received_date`를 저장하고, 발신자/제목은 별도로 검증한다. 기존의 시각 메타데이터와 새 날짜 전용 메타데이터를 혼합해 정밀도가 다른 순서 판단을 하지 않는다.

## 4. 처리량은 작은 배치로 늘린다

- 먼저 1건을 시험하고 저장 결과와 다음 행 이동을 검증한다. 그다음 몇 건의 짧은 배치를 거쳐 사용자가 확인할 수 있는 크기로 올린다. 이 지비톡 캡처는 한 실행 최대 30건을 사용한다.
- 고정 지연만 믿지 않는다. 입력 뒤 접근성 상태를 다시 읽고, 행과 본문이 모두 이전 지문에서 바뀐 뒤 같은 새 쌍이 연속 관찰될 때만 안정 상태로 판단한다. 한쪽만 먼저 바뀐 UIA 상태는 혼합 스냅샷으로 보고 기다린다. 취소 표식 예외 외에 제한 시간 안에 맞지 않으면 오류 사유를 체크포인트에 남기고 멈춘다.
- 각 배치 뒤 순번, 본문 해시, 행 반복, 체크포인트를 검사한 후 다음 배치를 시작한다. 측정된 처리량을 모르면 “2분이면 완료”처럼 보장하지 않는다.
- 이상 상태, 창 변경, 날짜 순서 역행, 빈 본문, 예상 밖 중복 이동이 보이면 즉시 정지하고 마지막 확정 저장 위치를 남긴다.
- 취소 placeholder처럼 목록 행과 본문이 모두 같은 문자열로 반복되는 항목은 행/본문 해시만으로 개별 메시지를 구분할 수 없다. 날짜와 발신자를 확인해도 앞서 저장한 placeholder와 둘 다 같으면 동일 메시지의 재방문인지 별도 메시지인지 추가 커서 증거가 필요하다. 모호한 행을 확정 저장하거나 다음으로 자동 진행하지 말고, 매니페스트·인접 커서·화면을 대조해 unresolved 상태로 기록한다.
- UI 매크로 실행 중 앱이 인증 화면으로 돌아오면 해당 배치는 중단 상태로 보존한다. 인증은 사용자가 직접 처리하고, 재개 후에는 관리함을 다시 찾고 현재 강조 행·미리보기·UIA 본문을 새로 읽는다. 이전 실행의 UI 선택이나 창 핸들이 살아 있다고 가정하지 않는다.

## 5. 쓰기 의도와 확정 상태를 분리한다

- 새 줄을 파일에 추가하기 전에 체크포인트에 기록할 줄, 기존 파일의 바이트 길이, 기존 앞부분 SHA-256을 저장하고 동기화한다.
- 추가 뒤 파일을 다시 읽어 기존 앞부분과 새 줄이 예상한 바이트와 일치하는지 확인한 후에만 확정 건수를 올린다.
- 재개할 때 체크포인트의 앞부분 길이와 해시를 현재 파일에 대조한다. 일치하지 않으면 파일을 고치거나 덮어쓰지 않고 멈춘다.
- 미확정 추가는 다음처럼 구분한다.
  - 파일 꼬리가 비어 있음: 쓰기 전 중단으로 보고 미확정 의도를 정리한 뒤 해당 항목을 다시 처리한다.
  - 예상한 줄 전체가 있음: 이미 기록된 항목을 확정 처리하고 그다음 항목부터 이어간다.
  - 꼬리가 예상 줄의 일부와 정확히 일치함: 확정 앞부분 해시가 맞을 때만 그 미완성 꼬리를 제거하고 다시 처리한다.
  - 앞부분 해시가 바뀌었거나 예상과 다른 꼬리가 있음: 원본을 보존하고 중단한다.
- 재개 커서는 선택 행의 지문과 순번/발생 횟수를 함께 기록한다. 화면이 커서와 맞지 않으면 기준점부터 저장한 행들을 차례로 대조하는 제한된 재탐색만 허용한다. 본문 해시가 다르면 중단한다. 본문은 같지만 행 지문만 달라졌다면 해당 본문이 저장 구간에서 한 번만 나타날 때만 일치로 인정하고, 같은 본문이 여러 번 있으면 중단한다.
- 경계 후보를 사람이 확인한 뒤 다음 호출을 할 때 현재 화면의 행/본문 지문이 체크포인트 후보와 모두 같으면 그 행에서 바로 이어간다. 후보와 다르면 안전하게 기준점부터 다시 찾는다. 불필요한 전체 목록 재탐색은 피하되, 화면 선택을 지문으로 확인할 수 없으면 속도보다 안전을 우선한다.
- 30건 배치 재개 때 현재 화면이 체크포인트의 `next_row` 행/본문 지문과 모두 일치하고 그 쌍이 기준 raw 및 이미 저장한 접두부와 겹치지 않으면 해당 커서에서 바로 이어간다. 일치하지 않거나 기존 쌍과 모호하게 겹치면 기준 앵커부터 저장 접두부를 다시 대조한다.
- 기간 경계를 확인했다면 경계 행 지문을 체크포인트에 저장해 그 행을 기록하기 전에 정지한다. 재개 시 현재 행 지문이나 본문 지문이 경계와 일치하면 저장하지 않는다.
- 과거 백필을 시작할 때 기준 범위의 가장 오래된 앵커 뒤쪽에 기준 raw JSONL이 이미 포함한 미검증 꼬리가 있으면, 행/본문 쌍이 유일하게 일치하는 항목만 건너뛰고 그다음 새 항목부터 기록한다. 같은 쌍이 여러 번 있거나 행/본문 중 하나만 겹치면 메시지를 추정해 넘기지 말고 중단한다. 기존 raw 전체는 읽기 전용으로 유지한다.

## 6. 복구는 임시 파일로 시험한다

실제 아카이브에 오류를 일부러 만들지 않는다. 임시 폴더와 모의 UI 상태로 최소한 아래 네 경우를 구성해 확인한다.

1. 체크포인트만 기록된 뒤 종료
2. JSONL 줄을 쓴 뒤 확정 체크포인트 전에 종료
3. 예상 JSONL 줄의 일부만 기록
4. 확정된 기존 앞부분을 바꾼 뒤 재개 시도

각 경우에 재개 결과, 행 수, 본문 해시, 파일 바이트, 체크포인트를 검사한다. 네 번째 경우에는 파일이 그대로 보존된 채 중단되어야 한다. 모의 시험은 복구 로직을 검증할 뿐, 실제 앱의 포커스나 전체 목록 순회를 검증하지는 않는다.

## 7. 원문과 최종 보관을 분리한다

- 사용자가 요청한 범위의 원문만 임시 캡처한다. 사진·첨부파일 저장은 별도 요청이 없다면 포함하지 않는다.
- 원문 캡처가 날짜·발신자·제목을 보증하지 않으면 월별 아카이브에 바로 넣지 않는다. 화면에서 메타데이터를 확인해 검증된 입력 파일을 만든 뒤 최종 보관한다.
- 현재 단계, 확인된 사실, 미검증 사항, 다음에 안전하게 할 일을 인계 문서에 남긴다. 과거 시점의 절차가 현재 지침처럼 보이지 않도록 최신 상태를 분명히 표시한다.
- 사용자가 컴퓨터를 써야 하거나 UI 자동화를 멈춘 동안에는 전경 입력을 중단한다. 이미 저장한 원문 해시·체크포인트·스크린샷을 재사용해 메타데이터 대조, JSONL 생성, 코드/문서 보완 같은 독립 작업을 진행한다. 확인된 행을 다시 캡처하지 말고 마지막 처리 순번과 임시 자료 경로를 인계한다.
- 화면에서 확인한 순번별 수신 시각·발신자를 CSV에 따로 기록하고, `scripts/build_archive_input.py`로 원문 순번/본문 해시, 월 범위, 최신순을 검증해 최종 입력을 만든다. UI가 중단된 동안에는 이 오프라인 대조를 진행할 수 있다. 기존 월별 파일과 원문이 다른 수신함 범위이거나 본문이 다르면 기존 파일에 억지로 추가하지 말고 출처가 분명한 별도 스냅샷을 만든다. 이 도구의 Markdown 출력은 기존 파일을 덮어쓰지 않는다.
- 증분 백업은 검증된 기존 raw 캡처를 읽기 전용 기준으로 삼고 새 출력 폴더에서 `Home`부터 시작한다. 기준의 행 지문과 본문 지문이 모두 일치하면 기존 경계 후보로 보고 그 행을 기록하지 않는다. 같은 내용의 메시지가 다시 올 수 있으므로 후보 행의 보이는 수신 시각·발신자를 기준 메타데이터와 대조하기 전에는 경계 완료로 간주하지 않는다. 한 지문만 일치하면 새 쪽지와 기존 쪽지를 구별할 수 없으므로 저장하지 않고 모호 상태로 멈춘다. 최대 30건마다 중단하며, 재개 시 `Home`부터 이미 저장한 신규 행의 두 지문이 모두 맞는지 확인한다. 기존 경계가 확인되지 않은 배치는 완료 처리하거나 월별 파일에 합치지 않는다. 메타데이터 대조 뒤 `build_archive_input.py --prepend-to`를 사용하면 모든 신규 수신 시각이 기존 월별 파일 맨 위의 최신 시각보다 더 최신인지 확인한 후에만 맨 앞에 합친다.
- 저장 범위는 양쪽 경계로 기록한다. 매니페스트의 `newest`는 새 도착분을 멈출 기준이고 `oldest`는 과거 쪽지를 이어 읽을 기준이다. 과거 방향은 먼저 Home부터 `oldest` 후보를 찾고 날짜·발신자를 사람이 확인한 뒤에만 캡처를 시작한다. 재개 때도 앵커와 이미 저장한 뒤쪽 prefix를 다시 대조하며, 완료된 과거 배치는 메타데이터를 확인하고 `--append-to`로 해당 월 파일의 가장 오래된 기록 뒤에 합친다. 한 월 범위를 넘어선 캡처는 월별로 분리해 검증한다.
- `captureOlderThanKnown`가 `paused-anchor-not-found`를 반환하면 먼저 체크포인트의 `saved_count`/JSONL 크기와 화면의 목록 끝을 확인한다. 기준 행이 없다는 이유만으로 `maxAnchorScanRows`를 키워 반복하지 않는다. 목록이 오래된 항목을 더 로드하는 경로가 확인되면 그 경로를 별도 단일 동작으로 관찰하고, 새 화면에서 앵커/본문 지문이 맞은 뒤에만 캡처를 재개한다.
- 보관 시 메시지 날짜는 기록한다. 시각은 요구하지 않으며, `captured_at`(로컬 수집 시각)을 수신 날짜로 대체하지 않는다. 날짜를 확인할 수 없으면 추정하지 말고 `date_status: missing`과 행 순번/지문을 누락 매니페스트에 기록한다. 검증된 기존 날짜가 있으면 순번과 행 지문이 일치하는 경우에만 사용한다.
- 다시 화면 작업을 시작할 때는 현재 선택과 체크포인트 커서를 대조한다. 커서가 일치하면 그 지점에서 이어가고, 다르면 저장 접두부를 확인한 뒤 제한된 재탐색으로 복구한다. 처음부터 반복하는 것을 기본값으로 삼지 않는다.
- 실제 키 경로를 찾을 때는 먼저 체크포인트의 마지막 행을 화면 머리글·본문과 맞춘 다음 `Down`을 딱 한 번 보내고, 새 행과 새 본문이 함께 갱신됐는지 즉시 확인한다. 2026-10-27에는 저장 커서 398번(2026-07-21 16:21)까지 대조한 뒤 이 절차로 7월 22일에서 7월 21일 행까지 한 번에 한 쪽지씩 이동하는 동작을 확인했다. 실제 캡처 배치는 실행 직후 사용자의 Escape로 중단되어 새 행 저장 여부를 추측하지 않았고, JSONL/체크포인트 재대조로 398행 그대로임을 확인했다. 이때도 `End`나 반복 입력을 사용하지 않는다.

## 8. 빠진 날짜는 지문을 고정해 별도 보강한다

- 메시지 날짜만 필요하면 `received_date: YYYY-MM-DD`를 기록한다. `captured_at`은 수집 시각이므로 수신 날짜로 사용하지 않는다. 날짜가 확인되지 않으면 앞뒤 날짜로 보간하지 않는다.
- 이미 캡처된 raw JSONL은 읽기 전용으로 둔다. 날짜 sidecar에는 원본 파일 SHA-256, 순번, 행 SHA-256, 본문 SHA-256, 확인 날짜, 판독 방법을 기록한다. `scripts/apply_date_backfill.py`로 새 날짜 보강본을 만들 때 모든 원본/매핑 지문과 날짜를 재검증하고, 한 행이라도 날짜가 남으면 출력하지 않는다.
- OCR은 후보 읽기에 쓸 수 있지만 숫자를 혼동할 수 있다. 2026-10-27 백필에서 화면의 `09.08`을 `09.03`, `09.18`을 `09.13`으로 잘못 읽은 사례를 발견했다. 의심 날짜를 주변 행이나 날짜 순서만으로 고치지 말고, 동일한 선택의 보이는 머리글을 다시 확인한 경우에만 수동 정정하고 `visible_header`와 판독 근거를 sidecar에 남긴다.
- 행/본문 지문이 고정된 다음 날짜를 읽는다. 날짜 판독 전후로 지문이 바뀌면 해당 값을 폐기하고 다시 관찰한다. 매핑은 최대 30행 단위로 저장·재개하고, 재개할 때 현재 지문과 체크포인트를 일치시킨다.
- 최종 확인은 raw와 보강본의 행 수, 연속 순번, 본문 해시, 원본 파일 해시, `received_date` 누락 수, 최신순 날짜 경계를 대조한다. sidecar가 원본을 가리키지 않거나 날짜가 충돌하면 멈춘다.

## 9. 발신자는 메시지마다 확인하고 별도 보강한다

- 발신자는 날짜 묶음만으로 채울 수 없다. 각 메시지의 보이는 발신자 표기와 `row_sha256`·`body_sha256`를 함께 묶는다. 본문 서명이나 전달된 원문에 등장하는 이름을 실제 발신자로 추정하지 않는다.
- UIA 트리에 발신자 머리글이 없으면 화면의 발신자 머리글/목록 행을 읽는다. OCR 문자열은 후보일 뿐이며, 화면과 대조하기 전에는 verified sender로 저장하지 않는다. OCR 결과와 화면이 다르거나 이름이 모호하면 해당 행에서 중단하고 비워 둔다.
- 목록 검색은 누락 행을 찾는 보조 수단이다. 검색 결과가 하나인지 확인하고, 선택 뒤 머리글·날짜·표시 제목과 원문 지문을 대조한다. 검색 탭을 닫거나 목록으로 돌아온 뒤에는 선택이 유지된다고 가정하지 않는다. 강조 행과 미리보기 불일치가 있으면 키를 보내지 않는다.
- 과거 발신자를 검색으로 보강할 때는 원본 본문에서 짧고 구별되는 구절을 고른다. 검색 입력 칸을 한 번 눌러 포커스를 만든 뒤 검색어는 키보드로 입력한다. 2026-10-28에는 검색 결과 행을 마우스로 선택한 다음 `Down` 한 번으로 그 결과 목록의 다음 행이 열리는 것을 관찰했다. 단, 한 번의 확인만으로 반복 이동·목록 끝 처리·모든 검색 탭에서의 동작을 일반화하지 않는다. 다음 행마다 화면 머리글과 날짜를 확인하고 전체 본문 지문을 대조한다.
- 검색 결과의 머리글 발신자·목록 날짜 `MM.DD`를 기록한 다음 선택 미리보기 전체 UIA 본문 SHA-256을 계산해 dated source의 `body_sha256`와 정확히 일치시키고, `received_date`의 월·일도 확인한다. UIA 접근성 트리에서는 본문 편집 요소의 `Value`가 `ID: 1022`로 끝나는 줄을 추출한다. 메시지 본문에 링크가 있으면 링크 요소에도 `Value:`가 생길 수 있으므로 단순히 트리에서 마지막 `Value:`를 고르면 본문 대신 URL을 해시할 수 있다. 날짜에 연도가 보이지 않으면 검증된 원본 연도를 붙인 사실과 화면의 원래 날짜 표기를 sidecar에 함께 적는다. 해시가 원본에 없거나 둘 이상과 맞거나 날짜가 다르면 그 후보를 건너뛴다. 전달 본문 속 발신자나 검색어 강조만으로 이름을 채우지 않는다.
- 검색 입력 컨트롤의 접근성 요소를 클릭한 뒤에도 포커스가 목록에 남아 있는 경우가 있었다. `focused_element`가 검색 편집란인지 확인한 뒤 입력한다. 포커스가 목록이면 입력하지 않고 새 상태를 읽어 편집란을 다시 선택한다. 2026-10-29 `아 그런거같네요 학기초는`은 검색 0건이었고, 더 짧은 `안될거같고`는 여러 후보를 반환했다. 0건은 부재 판정이 아니며, 반환된 후보는 날짜·발신자·본문 지문으로 골라야 한다.
- 전체 창 좌표 입력은 해당 상태의 전체 화면 screenshot ID와 함께 호출한다. 실제로 작은 겹침 `screenshot-0`(133×713)와 전체 관리함 `screenshot-1`(1300×760)이 함께 반환된 사례가 있었다. screenshot ID 없이 `(1177,56)`을 보내자 창 범위 오류가 났고 클릭은 실행되지 않았다. 재관찰 후 전체 screenshot ID를 지정해 검색창을 눌렀다. 검색은 새 포커스 확인 → 키보드로 질의 입력 → `Return` 실행 순으로 했으며, 질의 결과 탭은 추가로 열리고 기존 탭은 남았다. 각 단계에서 상태를 다시 읽고 이전 좌표·요소 인덱스를 재사용하지 않는다.
- 검색 결과가 없을 때는 검색이 본문을 토큰/구문 처리하는 방식이 확정되지 않았음을 고려해 더 짧고 넓은 구절로 다시 찾는다. `9월 16일 육상대회 인솔`은 결과가 없었지만 `보결안내`는 같은 자료의 09-14 항목을 찾았다. 검색 결과 탭을 바꾸면 새 상태부터 관찰하고, 좌표 클릭에는 작은 겹침 crop 대신 전체 창 screenshot ID를 붙인다.
- 기존 검증 메타데이터를 재사용할 때는 행 SHA-256, 본문 SHA-256, 수신 날짜의 세 값으로 원본과 1:1 매칭한다. 같은 취소 placeholder처럼 해시가 반복되면 날짜가 하나의 후보를 가리키지 않는 한 보강하지 않는다.
- 수동 확인은 원본 파일 SHA-256, 순번, 행/본문 SHA-256, 날짜, 화면 발신자, 판독 방법을 sidecar에 기록한다. 날짜 보강본과 발신자 보강본은 새 파일로 생성하고, 원본을 덮어쓰지 않는다. 판독되지 않은 행은 `sender_capture_status: missing`으로 표시한다.
- 새 live capture는 확인된 `senderReader`가 없으면 저장하지 않는다. `createVerifiedSenderReader(records)`는 `manually_verified: true`, 보이는 머리글/목록 근거, 순번/행/본문 지문이 모두 있는 항목만 받는다. 캡처 직전 현재 행/본문 지문을 다시 대조하므로 한 칸 이동이 지연되거나 선택이 달라지면 멈춘다.
- 발신자도 최대 30건씩 읽고 확인한다. 배치에는 순번별 날짜·발신자·행/본문 지문을 저장하고, 다음 배치 전에 누락/반복/오독 여부를 점검한다. OCR을 안정적으로 검증할 수 없는 상태에서는 자동 배치 수를 늘리지 않는다.
- 2026-10-28 검증에서 화면의 `이명숙`을 Windows 한국어 OCR이 머리글과 목록 행 crop 모두 `이영숙`으로 읽었다. crop을 좁혀도 오독이 남아 이 후보는 저장하지 않았다. 한 번의 OCR 성공이나 두 crop의 같은 OCR 값만으로 정확성을 입증할 수 없다. 상세 재현 및 수정 이력은 [troubleshooting.md](troubleshooting.md)에 기록했다.
- 2026-10-28 현재 선택 행에서 `Ctrl+C`를 한 번 보냈을 때 포커스는 메시지 본문 UIA 요소였고 클립보드 길이는 0이었다. 이것은 목록 행 복사 기능을 검증한 결과가 아니다. 복사를 시험하려면 먼저 의도한 컨트롤의 실제 포커스와 선택 텍스트를 확인하고, 복사 결과를 UIA/화면 값과 비교한다. 빈 클립보드나 본문만 복사된 결과를 sender 근거로 쓰지 않는다.

## 10. 발신자 월별 현황을 합칠 때

- 원본별 보강 JSONL은 그대로 두고 `scripts/build_sender_month_slices.py`로 별도 월별 파일과 감사를 만든다. optional `--new-october-jsonl`은 신규 10월 live capture를 같은 날짜 안에서 기존 자료보다 먼저 둔다.
- 집계 전 원본 JSONL의 본문 해시, 행/본문/날짜 중복, 원본별 순번을 확인한다. 월별 audit에는 입력 경로·SHA-256, 월별 행/발신자/누락 수, 출력 SHA-256을 기록한다. 출력 디렉터리는 재실행 시 덮어쓰지 않도록 매 실행마다 새 이름을 쓴다.
- 날짜만 있는 서로 다른 소스는 같은 날 안의 정확한 수신 시각을 보증하지 않는다. 출력 순서는 날짜와 출처 우선순위로 표현하고, 시각순으로 오해되지 않게 audit와 README에 한계를 명시한다.
- 사용자용 Markdown은 `scripts/render_sender_month_markdown.py`로 만든다. 원본 월별 JSONL 해시·날짜 순서·본문 지문·sender 집계가 검증되지 않으면 렌더링을 거부하며 `발신자 미확인`을 그대로 표시한다. 기존 대상 파일은 덮어쓰지 않는다.


## 2026-10-29 보강: 검색칸·본문 접근성 값의 stale 상태 처리

- 쪽지관리함 창 ID 731736에서는 검색칸을 클릭해도 AX `focused_element`가 `16 창 쪽지함 리스트`로 남는 관찰이 있었다. 이 창에서만 화면에 검색칸의 입력 커서가 보이고, 검색어 입력 후 해당 문자열이 입력칸에 나타난 것을 확인한 다음 Return을 보냈다. 새 검색 작업에서도 클릭 후 스크린샷을 확인하고, 입력한 문자열이 검색칸에 실제로 보이기 전에는 Return을 보내지 않는다. 문자열이 다른 영역에 나타나거나 커서가 불분명하면 즉시 멈추고 다시 관찰한다.
- 검색 결과 행을 바꾼 뒤 AX 본문 `Value`가 이전 탭 텍스트로 남을 수 있다. 새로 선택한 행의 화면 머리글(발신자·날짜·시각)과 전체 본문이 원본과 일치하는지 각각 확인한다. AX 본문이 앞 메시지의 내용과 같은 경우에는 그 값으로 SHA-256을 계산해 현재 메시지의 검증으로 쓰지 않는다.
- 증거 수준을 sidecar에 정확히 쓴다. AX 전체 본문이 원본의 `body_sha256`와 일치하면 `search-result-visible-header-and-exact-uia-body-sha256`를 쓴다. UIA 값이 stale이고 전체 본문이 화면에 읽히는 경우에는 `selected-row-header-and-full-visible-body-manual-match; UIA edit value remained stale from prior tab`을 쓰고 육안 대조임을 설명한다. 육안 확인에 UIA 해시 성공을 덧붙이지 않는다.
- 화면에서 본문 전체를 볼 수 없거나, 인용·전달 구간과 선택 쪽지 구간을 나눌 수 없거나, 날짜·발신자 후보가 둘 이상 남으면 sender를 기록하지 않는다. 첨부는 메시지 식별을 돕는 파일명 표시만 읽고, 열거나 저장하지 않는다.
- 검색 0건은 쪽지 부재를 뜻하지 않는다. seq5에서 긴 구절은 0건이었으나 `기록사항 없습니다`라는 짧은 구절은 5건을 반환했다. 고유성이 유지되는 범위에서 검색어를 줄이고, 다중 결과에서는 날짜·머리글·선택 본문을 대조한다.
- batch10은 9건을 더해 수동 맵 105건이 됐다. 출력은 search10 이름의 새 JSONL·월별 산출물로 만들고, 사용자 Markdown 4개를 교체하기 전에 기존 파일 네 개를 별도 백업 폴더에 보존했다. 적용 후 root와 staging의 각 SHA-256을 대조했다.


### 2026-10-29 검색형 검증에서 보강한 점

- 반복 검색은 키보드 입력 중심으로 한다. 검색창 포커스가 AX 상태에서 편집란으로 확인된 뒤 Ctrl+A, 검색어 입력, Return을 보낸다. 좌표 클릭 직후 포커스 응답이 이전 목록으로 남을 수 있으므로 새 상태를 다시 읽고 확인한다.
- 좌표 입력은 매번 최신 전체 창 screenshot ID와 함께 한다. 작은 겹침 crop의 화면 좌표를 전체 창 좌표로 쓰지 않는다. 선택 후에는 검색 목록의 실제 발신자/시각, 메시지 머리글, 전체 UIA 본문 지문을 함께 확인한다.
- 검색은 첨부 미리보기나 여러 날짜 후보를 포함해 여러 결과를 반환할 수 있다. 검색어가 일치한다는 사실만으로 seq를 지정하지 않는다. 날짜·머리글·전체 본문 SHA-256으로 원본 행을 확인한다.
- 전달·인용 본문에 기록된 발신자와 선택 쪽지의 실제 발신자는 다를 수 있다. seq366은 전달된 이창수 메시지에 대한 박순현 교장의 답장이므로, 실제 머리글 이름을 저장한다.
- 결과가 0건이거나 후보가 여러 개면 검색어를 더 짧게 바꾸거나 날짜가 맞는 후보를 열되, 어느 경우든 머리글과 본문 지문이 맞기 전까지 sidecar에 추가하지 않는다.

## 2026-10-29 batch12: 검색 재시도와 날짜 맵 정정

### 검색 매크로를 재현하는 순서

1. raw 원문에서 짧고 구별되는 구절을 고른다. 긴 구절 전체를 넣는 것보다 메시지의 고유한 핵심 표현을 우선한다.
2. 최신 전체 창 screenshot ID를 확인해 검색칸을 클릭하고 Ctrl+A 후 검색어를 입력한다. AX focus가 목록으로 남을 수 있으므로 화면의 커서와 입력 문자열이 검색칸 안에 보이는지 확인한다. 문자열이 보이기 전에는 Return을 누르지 않는다.
3. 검색을 실행하고 결과 수, 후보 목록의 발신자/날짜/시각을 확인한다. 검색이 자동 선택하지 않은 경우 의도한 후보 행을 선택한다.
4. 선택 뒤 실제 머리글과 날짜·시각을 확인하고 본문 전체를 raw source와 대조한다. 검색어 하이라이트만으로 sequence를 정하지 않는다.
5. 0건이면 결과 알림을 닫고 새 화면을 읽은 뒤 고유성을 유지하는 짧은 구절로 다시 검색한다. batch12에서는 ‘강사 네 분의 신분증 사본’ 0건 → ‘신분증 사본’ 5건, ‘안전하이 퀴즈’ 0건 → ‘당첨자 발표’ 1건으로 복구했다.
6. 다중 후보는 실제 머리글의 날짜/시각과 본문을 함께 비교한다. 예를 들어 5개 결과 중 seq27과 일치한 09-28 11:11 메시지만 선택했다. 후보가 여러 개 남으면 sidecar를 기록하지 않는다.

### 메타데이터와 근거 수준

- 인용·전달된 메시지의 이름과 발송 시간, 본문에 적힌 마감일은 현재 쪽지의 메타데이터가 아니다. sender/date/time은 선택된 쪽지 머리글에서 읽고, 본문은 원본 내용을 연결하는 증거로 쓴다.
- 날짜 맵이 틀렸으면 revision을 새로 만든다. 순번이 이어진다는 이유로 날짜를 채우거나 변경하지 않는다. correction log에는 sequence, 이전/새 날짜, 화면 머리글의 발신자·시각, 확인 이유를 넣는다. 수정된 맵으로 날짜 보강본을 새로 만들고 398행 coverage 및 원본 SHA를 확인한다.
- 화면 본문 전체를 raw 원문과 눈으로 대조했으면 manual-screen-body-match라고 기록한다. UIA 전체 본문을 가져와 SHA-256을 계산하고 source body hash와 일치시켰을 때만 exact UIA hash라고 기록한다. stale, 잘린 본문, 모호한 인용 경계, 복수의 본문 후보가 있으면 sender를 확정하지 않는다.
- 첨부 아이콘이나 인라인 사진은 식별에 필요한 범위에서 화면에 표시된 사실만 기록한다. 사용자 범위에서 제외된 첨부는 열거나 저장하지 않는다.
- 새 발신자 sidecar는 날짜 포함 source SHA, sequence, row/body SHA, received_date, 화면 머리글, 검색어, 결과 수, 검증 방식을 묶는다. 새 dated JSONL에서 apply_sender_backfill.py로 적용하고, 월별 집계 후 Markdown을 다시 만든다.
- 사용자 문서 교체 전에는 README와 각 월별 파일의 기존 버전을 별도 새 폴더에 보존한다. 교체 뒤에는 staging 결과와 최종 파일 네 개 각각의 SHA-256을 대조한다. 다음 재개를 위해 마지막 앱 선택/검색어, 다음 미확인 sequence, 배치별 count/hash를 NEXT_STEPS.md에 남긴다.
