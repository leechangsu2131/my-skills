# GBTalk 트러블슈팅 및 수정 이력

이 문서에는 실제 작업에서 관찰한 오류, 수정, 아직 해결되지 않은 문제만 기록한다. 현재 재개 위치와 상태는 [`../NEXT_STEPS.md`](../NEXT_STEPS.md), 반복해서 적용할 원칙은 [`keyboard-macro-methodology.md`](keyboard-macro-methodology.md)를 본다. 새 UI 작업 전에는 현재 상태와 관련된 항목을 확인한다.

원인이 확정되지 않은 경우 원인 추정과 관찰 사실을 구분한다. 수정 뒤 실제 앱에서 확인하지 못한 동작은 해결 완료로 표시하지 않는다.

## UI 포커스와 목록 이동

### `End` 키가 여러 행을 건너뜀

- **관찰:** 받은쪽지 목록에서 `End` 한 번이 여러 쪽지를 건너뛴 사례가 있다.
- **대응:** `End`를 연속 탐색에 사용하지 않는다. `Home` 또는 한 번의 `↓` 뒤 목록 행·머리글·본문 변화를 확인한다.
- **상태:** 앱의 `End` 동작은 안전한 이동 방법으로 검증되지 않았다.

### 검색 탭을 닫은 뒤 선택 위치가 초기화됨

- **관찰:** 2026-10-22 검색 결과 탭을 닫아 전체 목록으로 돌아오자 선택이 최신 행으로 초기화됐다. 그 상태에서 `Down` 한 번을 보내니 기준보다 최신 날짜가 선택되어 날짜 역행으로 중단됐다.
- **대응:** 검색 전 선택 위치가 유지된다고 가정하지 않는다. 화면과 저장 지문으로 기준 행을 다시 찾고, 확인되지 않으면 이동·저장을 멈춘다.
- **상태:** stale selection을 지문으로 복구하는 규칙은 적용됐다. 검색 탭 복귀의 포커스/선택 보존은 검증되지 않았다.

### 본문에서 `Tab`/`Shift+Tab`을 보내면 목록 포커스가 보장되지 않음

- **관찰:** 본문에서 `Tab`을 보내면 스크롤바를 거쳐 `삭제` 버튼까지 이동했다. `Shift+Tab` 뒤에는 본문 패널 루트가 포커스를 받았는데 넓은 창 판정이 이를 목록 포커스로 오인한 적이 있다. 이 잘못된 포커스 판정으로 재개 때 한 행이 추가 저장된 뒤 중단됐다.
- **수정:** 포커스 판정을 일반 `창` 여부가 아니라 `UltariList` 행의 자식 관계와 실제 강조 행으로 좁혔다. 고정 Tab 횟수는 쓰지 않는다.
- **상태:** 판정 로직은 좁혔지만, 행 클릭을 포함한 포커스 복구 전체가 현재 앱에서 안정적이라는 뜻은 아니다. 아래 2026-10-27 인덱스 클릭 사례를 함께 본다.

### UIA 행 클릭과 화면 선택이 다를 수 있음

- **관찰:** 2026-10-26에는 요소 클릭이 `coordinate input geometry is unavailable` 또는 캐시되지 않은 요소 오류를 냈다. 2026-10-27에는 요소 인덱스 `10` 클릭 후 화면은 2026-07-22 12:49 행을 강조했지만 UIA 행 텍스트는 7월 21일 휴대폰 습득 행, UIA 본문은 7월 22일 메시지를 가리켰다.
- **대응:** 인덱스가 현재 트리에서 반환됐거나 클릭 도구가 성공했다고 해도 선택 행으로 간주하지 않는다. 클릭 뒤 새 스크린샷과 접근성 트리를 읽어 강조 행·머리글·본문·UIA 행/본문이 같은 쪽지인지 비교한다. 불일치하면 추가 입력을 멈춘다.
- **상태:** UIA 인덱스 클릭으로 목록 포커스를 회복하는 경로는 신뢰할 수 있다고 검증되지 않았다. 확정된 대체 경로가 없다.

### 전체 화면에서 행을 다시 선택해도 UIA 목록 행이 이전 값으로 남음

- **관찰 (2026-10-27):** 재개 시 전체 관리함 화면의 강조 행과 머리글·본문은 김경영 교감의 2026-07-22 12:49 `[2027년 교원 명예퇴직 희망자 수요 조사]`를 가리켰다. 전체 화면에서 그 행을 다시 선택한 뒤에도 UIA `UltariList` 행과 `focused_element`는 2026-07-21 16:09 `휴대폰 습득!`을 반환했다. 창 핸들을 새로 받아 다시 조회해도 UIA 행은 갱신되지 않았다.
- **추가 관찰:** 스크린샷 배열에는 작은 겹침 영역과 전체 관리함 화면이 함께 들어올 수 있다. 배열의 첫 스크린샷은 133×713 영역이었고, 이를 전체 창 좌표로 착각한 첫 클릭은 행을 선택하지 못했다. 재관찰 뒤 1300×760 전체 관리함 스크린샷을 기준으로 다시 선택했으며, 화면 행/머리글/본문은 일치했지만 UIA 목록 행은 그대로였다.
- **코드상 주의:** `capture_macro.mjs`의 `isInboxRowFocus`는 포커스 인덱스가 접근성 트리의 첫 `UltariList` 행 인덱스와 같은지 확인한다. 이 검사는 화면의 강조 행과 해당 UIA 행의 내용이 같은지 증명하지 않는다. 포커스가 행 인덱스라는 사실만으로 현재 메시지를 확정하지 않는다.
- **대응 및 상태:** `Home`/`↓`와 helper 실행을 보류했다. JSONL·체크포인트 모두 398행 그대로다. 미해결이며 화면 행·머리글·본문과 UIA 행·본문이 다시 일치할 때까지 캡처하지 않는다.
- **추가 관찰:** 이후 같은 창을 다시 읽었을 때 목록은 7월 22일 12:49 최수민 행을 강조했지만 미리보기는 같은 시각 김경영 교감의 조사 쪽지에 남아 있었다. UIA 행은 계속 7월 21일 `휴대폰 습득!`을 반환했고, 읽지 않은 쪽지 수도 관찰 사이 24에서 25로 바뀌었다. 원인은 확정되지 않았으며 새 메시지 도착이나 화면 갱신 문제로 단정하지 않는다.
- **대응:** 화면 행과 미리보기도 맞지 않는 동안에는 키 경로 탐색을 보류한다. 다음 키 탐색은 안정된 기준 화면에서 한 번에 하나씩 시험하는 [방법론 절차](keyboard-macro-methodology.md)를 따른다.

### 재생 커서 확인 뒤 다음 `↓`에서 목록 포커스 상실

- **관찰:** 2026-10-27 `captureOlderThanKnown(maxItems: 30)` 재개에서 기존 398행을 다시 대조해 `replay_cursor.sequence: 398`까지 도달했다. 다음 한 칸 이동에서 포커스 오류가 났다. JSONL은 398행·352,806바이트 그대로이고 접두 해시가 체크포인트와 일치한다. 체크포인트는 `paused-ui-sync-error`, `next_row: null`이다.
- **복구 시도:** 오류 직후 화면/UIA가 7월 21일 16:10 후보를 가리켰지만, 뒤이은 인덱스 클릭 후 화면과 UIA가 서로 다른 7월 21일/22일 메시지를 가리켜 현재 선택을 확정할 수 없게 됐다.
- **대응:** `replay_cursor`는 마지막으로 대조한 저장 행이지, 현재 화면이 그 행에 남아 있다는 보증이 아니다. 현재 화면과 UIA가 일치하지 않으면 재생 커서만으로 다음 행을 추정하거나 캡처를 재호출하지 않는다.
- **상태:** 미해결. 다음 실행은 창 상태를 새로 관찰하고, 안전한 커서 복구 경로가 확인되기 전까지 키를 보내지 않는다. 현재 상세 상태는 [`NEXT_STEPS.md`](../NEXT_STEPS.md)의 최신 재개 기준을 따른다.

## UIA 본문과 날짜 판독

### 취소된 쪽지의 미리보기 값이 이전 본문으로 남음

- **관찰:** 선택 행 텍스트가 정확히 `취소된 메시지입니다.`인데 미리보기 UIA 편집 값은 이전 쪽지 본문을 계속 반환한 사례가 있다.
- **수정:** 이 정확한 placeholder 행은 미리보기 값 대신 목록의 취소 문구를 본문으로 사용하고 `recalled-placeholder`로 저장한다. 다른 행은 행/본문 지문 불일치가 해소되지 않으면 저장하지 않는다.
- **상태:** 캡처 helper에 반영됐다. 유사 문구나 다른 UI 상태에 일반화하지 않는다.

### 이동 직후 행과 본문이 서로 다른 시점으로 갱신됨

- **관찰:** `↓` 직후 UIA 트리가 선택 행만 또는 본문만 먼저 갱신한 혼합 상태를 반환한 적이 있다.
- **수정:** 두 지문이 모두 이전 값과 달라지고, 동일한 새 행/본문 쌍이 연속 관찰된 뒤에만 이동 완료로 본다. 제한 횟수 안에 안정되지 않으면 체크포인트에 오류를 남기고 멈춘다.
- **상태:** `capture_macro.mjs`에 안정화 조건이 적용됐고 모의 목록에서 확인했다. 실제 앱 전체 순회 성공을 보증하지 않는다.

### OCR이 오전·오후 시각을 월/일로 오인함

- **관찰:** `오전 09:12`, `오후 12:01` 같은 숫자 토큰이 날짜 후보로 잘못 읽힐 수 있었다. 백필 seq366은 화면 머리글 `08.05`가 OCR에서 잘못 읽혔고, seq367은 `07.28`이 `07.23`으로 잘못 읽혔다.
- **수정:** 오전/오후 표기 뒤에 있는 시각 토큰을 날짜 후보에서 제외했다. seq366·367은 화면 머리글을 확인해 백업을 만든 뒤 개별 날짜를 정정하고 증거를 기록했다.
- **상태:** parser의 시간 토큰 필터는 적용됐고 예시로 확인했다. OCR 날짜가 의심되면 해당 메시지 머리글을 확인하며 주변 날짜만으로 추측하지 않는다.

### 동일한 취소 placeholder가 기준 자료에 반복됨

- **관찰:** 취소 문구는 행/본문 해시가 여러 기존 메시지와 완전히 같을 수 있어 해시만으로 신규 메시지와 재방문을 구별할 수 없다.
- **대응:** 화면의 수신 날짜·발신자, 전체 기준 매치 순번, 바로 앞 저장 커서를 함께 검증한다. helper의 `confirmedDistinctCandidate` 조건이 모두 맞을 때만 별도 쪽지로 허용한다.
- **상태:** 예외 검증과 재개 검증이 helper 및 모의 목록에 반영됐다. 확인 증거가 현재 화면/커서와 다르면 저장하지 않는다.

## JSONL·체크포인트 복구

### 기록 시점별 중단과 파일 앞부분 변경

- **관찰 및 검증:** 기록 전 종료, 줄 기록 후 확정 전 종료, 부분 기록, 기존 파일 앞부분 변조를 임시 파일로 구성해 복구를 확인했다.
- **수정:** 쓰기 전에 기존 바이트 길이와 SHA-256을 체크포인트에 저장한다. 재개 때 기존 앞부분과 미확정 추가를 함께 검증하고, 불일치면 파일을 고치지 않고 멈춘다.
- **상태:** 네 경우의 임시 검증을 통과했다. 실제 아카이브에 오류를 만들어 시험하지 않는다.

### 기존 캡처 꼬리의 중복 행

- **관찰:** 원본 과거 백필 265행 중 10·11번이 각각 8·9번과 같은 중복 캡처로 확인됐다.
- **수정:** 원본은 보존하고 별도 정정본 263행을 만들어 후속 캡처를 이어갔다. 이후 중복 꼬리 62행은 검토용 파일로 분리했다.
- **상태:** 현재 작업 출력은 별도 `continuation-263` 폴더의 398행이다. 원본/정정본/검토용 꼬리를 합치거나 원본을 덮어쓰지 않는다.
