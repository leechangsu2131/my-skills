# 주간학습안내 NEIS 화면 분석

## 분석 범위

Playwright로 사용자가 로그인한 Chrome `127.0.0.1:9222` 세션의 NEIS 앱 인스턴스를 조사했습니다. 원래 작성 화면에 미저장 표시가 있어 별도 탭에 작성 화면을 열고 정상 조회만 수행했습니다. 원본 데이터 값과 주간학습 문구는 출력·보관하지 않았고, 저장·삭제 버튼은 누르지 않았습니다.

라이브 `dsAllMenu`에서 메뉴를 대조한 결과:

| 메뉴 | 메뉴 ID | 페이지 ID |
|---|---|---|
| 주간학습안내작성 | `AMELS40031` | `edu/sw/els/edc/tm/els_edctm06_m00` |
| 주간학습안내조회 | `AMELS40032` | `edu/sw/els/edc/tm/els_edctm06_m02` |

이번에 열린 화면은 `m00` 작성 화면입니다. 따라서 아래 제출 구성은 해당 페이지 앱에서 관찰한 설정이며, `m02` 조회 화면의 제출 설정이라고 단정하지 않습니다.

## 확인된 데이터 구조

작성 화면에서 `dsWikLrn`은 주간학습 그리드이며, 다음과 같은 요일별 열 구조입니다. 각 요일 접두사는 `mon`, `tue`, `wed`, `thu`, `fri`입니다.

- 행 기본값: `pir`, `pirNm` — 교시와 교시 표시값
- 날짜 및 과목: `<day>AllTiYmd`, `<day>EtbSbjtCd`, `<day>EtbSbjtNm`
- 학습 단원·내용: `<day>WikLrnUitNm`, `<day>WikLrnCn`
- 차시 정보: `<day>WikLrnRlvtTmsValue`, `<day>WikLrnAllTmsValue`, `<day>SeqSn`
- 교과서 쪽 정보: `<day>WikLrnPgeValue`, `<day>WikLrnAtaPgeValue`

관찰 시점의 화면 구조에서 `dsWeekList`는 주차 목록(`weekCntNm`, `weekCnt`, `weekBgngYmd`, `weekEndYmd`)을 제공했습니다. 행 수는 `dsWeekList` 27, `dsWikLrn` 8이었습니다. 이는 당시 열린 화면의 행 수일 뿐, 항상 같은 고정값이라는 뜻은 아닙니다.

따라서 오늘 수업 카드의 기본 정규화는 응답의 각 교시 행을 요일별 레코드로 펼쳐 `<day>AllTiYmd`를 날짜로, `pir`/`pirNm`을 교시로, `<day>EtbSbjtNm`을 과목으로, `<day>WikLrnCn`을 학습내용으로 매핑하는 방식이 적절합니다. `<day>WikLrnUitNm`, 차시, 쪽수는 선택 항목으로 두고 날짜가 오늘인 레코드만 남깁니다. 시간표와 결합할 때는 날짜와 교시를 키로 삼고, 과목이나 내용이 비어 있는 레코드는 화면 정책에 따라 제외하거나 빈 수업으로 표시합니다. 이 정규화는 실제 조회 응답의 필드 구조에 기반한 설계 제안이며 운영 자료의 예외는 추가 확인해야 합니다.

## 페이지에 설정된 조회·저장 제출

앱 인스턴스의 eXBuilder 제출 설정에서 다음 action 경로와 데이터 바인딩을 확인했습니다. 표는 페이지에 등록된 설정이고, 실제 요청·응답을 정상 조회로 확인한 결과는 아래 별도 절에 기록합니다.

| 제출 ID | 역할 | Action 경로 | 요청 데이터 | 응답 데이터 |
|---|---|---|---|---|
| `subSelectWikInfo` | 주간학습 정보 조회 | `/els_edc_tm06_003.do` | `dmSearch`, `_SWCDATA` 별칭의 `dmSearch` | `dsWikLrn` |
| `subSelectHcnt` | 시수 정보 조회 | `/els_edc_tm06_002.do` | `dmSearch`, `_SWCDATA` 별칭의 `dmSearch` | `dsHcntList` |
| `subWikInfoSave` | 주간학습 저장 | `/els_edc_tm06_004.do` | `dsWikLrn`, `dmSearch` | 구성된 응답 데이터 없음 |
| `subSaveAllWikLrn` | 주간학습 전체 저장 | `/els_edc_tm06_008.do` | `dmSearch` | 구성된 응답 데이터 없음 |

### 실제 조회 요청 캡처

2026-11-12, 별도 Playwright 탭에서 `주간학습안내작성`(`m00`)의 오늘이 포함된 주차를 선택한 채 화면의 조회 버튼을 눌렀습니다. 원래 사용 탭의 미저장 표시는 전후 동일했고, 새 탭에서도 저장 동작은 실행하지 않았습니다. 요청·응답 본문 값은 출력하거나 보관하지 않고 구조만 확인했습니다.

| POST 경로 | 응답 | 관찰 결과 |
|---|---|---|
| `/els_edc_tm06_002.do` | HTTP 200 | `dsHcntList` 3행. 과목별 동적 열 이름이 있어 고정 스키마로 취급하지 않습니다. |
| `/els_edc_tm06_003.do` | HTTP 200 | `dsWikLrn` 8행. 각 행은 교시이며, 요일별 날짜·과목·단원·학습내용·교과서 쪽·차시 필드를 가로로 담습니다. |

두 요청의 본문은 최상위 `data` 아래 `dmSearch`, `_AUTHDATA`, `_SWCDATA`를 포함했습니다. 인증·학교·학급·학습 내용 값은 저장하지 않았습니다. 서버 응답의 요일별 필드에는 화면 데이터셋에 바인딩되지 않은 `<day>WikLrnUitValue` 보조 필드도 있었습니다. 행 수와 응답 열은 관찰 당시 값이며 고정값으로 가정하면 안 됩니다.

조회 응답을 교사용 데이터로 바꿀 때는 교시 행을 월~금별로 펼쳐 다음과 같은 정규 레코드로 변환할 수 있습니다: `date`, `period`, `subject`, `unit`, `learningContent`, `textbookPage`, `lessonNumber`, `totalLessons`. 시간표와는 `date + period`로 결합합니다. 실제 수업 문구는 스킬 문서나 디버그 로그에 복사하지 않습니다.


같은 세션의 `주간학습안내조회`(`m02`)도 확인했습니다. 화면 진입 때 `/els_edc_tm06_001.do` 초기화 요청이 발생했지만, 그 화면의 조회 버튼은 데이터 `.do` 요청 대신 Crownix 보고서 미리보기를 열었습니다. 따라서 m02 버튼 동작을 주간학습 데이터 조회로 간주하지 않습니다. 이번에 실제 데이터 응답까지 검증된 읽기 흐름은 m00의 `/002`와 `/003`입니다. 메뉴 화면이 다르면 경로 접미사만으로 업무 의미를 추정하지 않습니다.

메뉴를 여는 과정에서 NEIS가 POST `/saveFavorites.do`도 자동 발생시켰습니다. 본문 키는 `dmFavorites`, `_AUTHDATA`였고 값과 효과는 조사하지 않았습니다. 이 자동 요청과 업무 데이터 저장 제출을 구분합니다.

### 월 단위 조회 확인

2026년 11월을 시험할 때 `dsWeekList`에서 월요일~금요일 수업일이 11월에 포함되는 주차 5개를 조회했습니다. 주차 데이터에는 하루 8교시 행이 있었고, `/els_edc_tm06_003.do` 응답은 다섯 주 모두 HTTP 200이었습니다. 각 주 응답의 `<day>AllTiYmd`를 11월 1~30일로 필터링해 21일, 109개 수업 항목을 확인했습니다. 10월 26일~11월 1일 주차는 11월 날짜가 일요일뿐이라 평일 수업 조회 대상에서 제외했습니다.

월 단위 전용 응답은 확인하지 않았습니다. 따라서 월 조회는 `dsWeekList`에서 대상 월과 겹치는 평일 주차를 찾아 주간 조회를 반복하고, 응답을 날짜별로 펼친 뒤 목표 월 범위만 남기는 방식으로 구성합니다. 위 행 수는 당시 교육과정 데이터에 한정된 실측치입니다. 조회 후 분석 탭은 현재 주차로 복원했고, 기존 작성 탭의 수정 상태는 전후 동일했습니다.

`dmSearch` 필드는 `shlCd`, `ayr`, `sem`, `grd`, `clsCd`, `weekCnt`, `weekBgngYmd`, `weekEndYmd`, `semBgngYmd`, `semEndYmd`, `ayrAuthType`로 확인했습니다. 요청값, 학교·학급 식별값, 학습 내용은 문서에 저장하지 않았습니다.

## 작업 안전 메모

- 읽기 제출과 저장 제출은 별도 객체입니다. 이 분석만으로 저장을 실행하거나 요청을 재현하지 않습니다.
- 작성 화면을 재조회하거나 다른 페이지로 옮기기 전에 모든 수정 가능한 데이터셋의 `isModified()`를 확인합니다. 하나라도 `true`이면 사용자의 미저장 작업을 보존하고 중단합니다.
- 원래 작성 화면의 `dsEtbSbjt`와 `dsExMessage`는 수정 상태였습니다. 해당 데이터 값은 읽지 않고 보존했으며, 별도 탭에서 조회해 원본 탭의 수정 상태가 바뀌지 않았음을 확인했습니다.
- 새 탭의 `dsWikLrn`은 조회 전후 모두 `isModified() === false`였습니다. 조회와 저장은 별도 흐름으로 유지하고, 개인정보가 포함된 원문 요청·응답은 저장하지 않습니다.
