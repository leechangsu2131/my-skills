# 학교 기물 대장 · 공간 사용 관리 + 3D 현황

학교 담당자가 구글 시트 하나로 (1) 기물 대장, (2) 교시별 공간 사용 신청·주간표, (3) 물품의 현재 위치를 관리하고, 선생님들은 링크 하나로 3D 화면에서 보고 신청하게 만드는 작업을 반복 가능하게 정리한 스킬이다.

## 이 PC에서 쓸 때
- 학교별 설정 JSON, 생성한 xlsx, 미리보기 html, QR PDF 같은 **결과물은 저장소가 아니라** `내 문서\my-skills-data\admin-school-facility\`에 둔다(공개 저장소라 학교 배치·교사 명단이 새면 안 된다).
- 웹앱 주소·접근 코드·관리자 코드는 중앙 `.env`에 `ADMIN_SCHOOL_FACILITY__` 접두로 적는다. 실제 코드값은 Apps Script 스크립트 속성에 넣는다.
- 원본: claude.ai에서 만든 `school-facility-tracker.skill` 패키지(2026-11-20 가져옴).

## 구성물
- `scripts/build_sheet.py`: 학교별 설정(JSON)으로 관리 시트 xlsx를 생성한다. 수식·드롭다운·조건부 서식이 모두 들어 있어 구글 시트로 열면 그대로 동작한다.
- `assets/apps_script/Code.gs`, `Index.html`: 시트에 연결해 쓰는 3D 웹앱(three.js). 보기 + 사용 신청 + 물품 위치.
- `scripts/extract_floorplan.py`: 엑셀로 그려 둔 학교 배치도(칸에 방 이름·호수를 적은 도면)에서 방 목록과 대략적인 위치를 뽑아 JSON 초안을 만든다.
- `scripts/make_qr_pdf.py`: 학생용 교실 QR 인쇄 PDF(A4 6칸, 방 이름 + QR + 사용법)를 만든다. 웹앱 배포 주소가 있어야 한다.
- `assets/duel_supabase/`: 두 학생이 QR로 만나 겨루는 퀴즈 듀얼(Supabase). 스키마·서버 함수(SQL), 예시 문제, 학생 화면 1개, 설치 안내(README), 서버 규칙 시험.
- `scripts/make_duel_preview.py`: 위 듀얼 화면을 가짜 Supabase와 묶어 같은 브라우저 두 탭에서 겨뤄 보는 미리보기를 만든다.
- `scripts/make_stl.py`: 학교 배치로 3D 프린터용 층별 STL(돌하우스 모형)을 만든다. trimesh·shapely·manifold3d 필요.
- `scripts/hwpx_tables.py`: 한글(.hwpx) 문서의 표를 격자로 뽑는다(방과후·돌봄 시간표 등).
- `scripts/test_server.js`: Code.gs 서버 규칙(PIN·대여·승인·관리자) 시험. 가짜 시트로 node에서 돌린다.
- `assets/apps_script/Chatbot.gs`: 카카오톡 챗봇(대여·반납·예약·빈곳·내 신청). Code.gs와 같은 프로젝트에 파일로 추가한다. 시험: `scripts/test_chatbot.js`.
- `assets/kakao/cloudflare_router.js`: 스쿨투두 카톡 채널 하나로 일정DB와 시설 시트를 나눠 보내는 중계기. 시험: `scripts/test_router.mjs`.
- `references/kakao-chatbot.md`: 챗봇 설치 순서, 선생님 연결, 카톡에서 하는 말, 한계.
- `scripts/make_preview.py`: 대화 안에서 바로 보여 줄 미리보기 HTML(가짜 백엔드 + 샘플 데이터)을 만든다.
- `assets/config.example.json`: 설정 예시(공간 10개, 교시 9개, 4층 배치, 여러 층을 쓰는 강당 포함).
- `references/design-notes.md`: 시트 구조, 접근 제어, 배포 체크리스트, 함정. 설계를 바꾸거나 막힐 때 읽는다.

## 작업 순서

### 1. 학교 정보 모으기
이미 대화에서 알려진 것은 다시 묻지 않는다. 부족한 것만 한 번에 한 가지씩 묻는다.
- 공간 목록(사용 신청 대상)과 보관 장소(창고·교무실 등 신청 대상이 아닌 곳)
- 교시 구성과 시간(점심·방과후 포함 여부)
- 건물 층수와 층별 공간 배치(대략적인 순서만 있어도 충분). 정확한 평면도는 없어도 된다.
- **여러 층을 함께 쓰는 공간**(강당, 급식실·조리실, 오픈 계단 공간 등)이 있는지. 있으면 시작층·끝층을 다르게 적는다.
- 학교에서 엑셀 배치도를 갖고 있으면 받아서 2-1 단계로 읽는다.
- 누가 쓰는지: 입력하는 사람(관리자)과 보기·신청만 하는 사람(교사)의 구분
- 구글 계정 환경: 학교 도메인(Workspace)인지 개인 계정인지 (접근 제어 방식이 달라진다)

사용자가 구글 시트, 엑셀, 직접 코드 중 아직 정하지 않았다면 이 스킬은 구글 시트를 전제로 한다고 알리고 확인한다.

### 2-1. 엑셀 배치도가 있을 때 (선택)
```bash
python scripts/extract_floorplan.py --xlsx 배치도.xlsx --sheet <시트명> --floor-tops 1:1,2:28,3:56 --out rooms.json
```
- 층이 한 시트에 세로로 이어져 있으면 `--floor-tops`에 층별 시작 행을 준다(층 글자 '1층' 등이 각 구역 안에 있는지 이미지로 변환해 확인하면 정확하다).
- 결과는 **초안**이다. `conf`가 낮음/번호만/이름만인 줄은 사람이 그린 도면의 이름-호수 짝짓기가 어긋났을 수 있으니 사용자에게 확인한다. 엑셀이 학급 표기('1-1')를 날짜로 바꿔 놓은 칸은 스크립트가 되돌린다. 호수 중복이나 오타로 보이는 값은 고치지 말고 알려 준다.
- 사용자가 확인한 뒤에 여러 층 공간을 하나의 블록으로 합치고(`[이름, 시작층, 끝층, x, y, 가로, 세로]`), 겹치는 블록을 줄이고, 신청 대상 공간을 고른다. 이 정리는 학교마다 달라서 스크립트 대신 간단한 일회성 코드로 한다.
- 층별 평면을 matplotlib로 그려 겹침과 위치를 눈으로 점검한다.

### 2. 설정 파일 만들고 시트 생성
`assets/config.example.json`을 복사해 학교 값으로 고친 뒤 실행한다.
```bash
python scripts/build_sheet.py --config my_config.json --out 학교_관리시트.xlsx
# 수식 오류 확인: xlsx 스킬(anthropic-skills:xlsx)의 recalc 절차를 따른다
```
- `people`(신청자 명단, 최대 200명)을 채우면 신청 화면이 이름 선택으로 바뀌고, 같은 사람이 같은 날 같은 교시에 두 곳을 신청하는 것을 정확히 막는다(공간 중복은 항상 막는다). 비우면 직접 입력이라 오타로 우회될 수 있다고 알린다.
- 신청 대상 공간(`spaces`)은 50개, 보관 장소(배치의 모든 방 + `extra_places`)는 240개, 교시는 20개까지 지원한다.
- `layout`은 `[공간, 시작층, 끝층, X, Y, 가로, 세로, 높이(선택)]`. 한 층만 쓰면 시작층=끝층, 여러 층을 쓰면 끝층을 크게 적는다(높이는 층수에 맞춰 자동 계산). 같은 X·Y에 층만 다르게 쓰면 위층에 쌓인다.
- `layout`에는 건물의 모든 방을 넣어도 되지만, **사용 신청을 받을 방만 `spaces`에 같은 이름으로** 넣는다. `spaces`에 없는 방은 3D에서 '신청 대상 아님'(옅은 파란색)으로 보이고 물품 위치만 표시된다. 이름이 다르면 신청 대상으로 인식되지 않는다.
- 생성 후 `xlsx` 스킬(anthropic-skills:xlsx)의 지침을 먼저 읽고 결과 파일을 제시한다. 첫 줄 예시 행은 사용 전에 지우도록 안내한다.

### 2-1b. 교육과정·시간표 문서가 있을 때
- 시정표는 `periods`에, 정규 수업·방과후 프로그램(특별실 사용표, 돌봄 시간표 등)은 `fixed_schedule`에 넣는다. 한글 파일은 `scripts/hwpx_tables.py`로 읽는다. 표는 이미지로 읽고 검증한다(`references/design-notes.md`의 '정규 수업' 항목). 교사 이름은 옮기지 않는다.

### 2-2. 학생용 빈 교실(QR)이 필요할 때
- `student_rooms`에 학생이 쓸 수 있는 공간을 적는다(설정 I열). 어느 방을 개방할지는 학교가 정하므로 임의로 정했다면 알리고 확인한다.
- 웹앱 학생 화면: `웹앱주소?mode=student`. QR: `python scripts/make_qr_pdf.py --url <배포주소> --config my_config.json --out QR.pdf` (스크립트 속성 `STUDENT_CODE`를 쓰면 `--code`도 같은 값). 배포 주소는 사용자가 배포한 뒤에만 알 수 있으니 가짜 주소로 만든 PDF를 최종본처럼 주지 않는다.
- 학생 화면에는 선생님 이름·물품을 보내지 않고, 학생은 실명 대신 학급·번호나 별명을 쓰게 한다. IP·위치를 수집하지 않는다. 자세한 규칙은 `references/design-notes.md`의 '학생용' 항목.

### 2-2b. 기물 대여·승인·관리자가 필요할 때
- `lendable_categories`(대여 가능 분류), `approval_spaces`(관리자 승인 필요 공간)를 설정에 넣고, `people`(신청자 명단)을 채운다. 접근 방식은 접근 코드 + 명단 + 개인 PIN, 기물은 자동 승인, 공간은 자동 확정 + 행사용 공간만 승인으로 시작한다(사용자가 정했다).
- 웹앱 배포 때 스크립트 속성 `ADMIN_CODE`(관리자 화면)도 설정하게 안내한다. 서버 규칙을 고치면 `node scripts/test_server.js`(챗봇을 쓰면 `test_chatbot.js`도)를 먼저 돌린다.
- PIN·관리자 코드의 한계(개인 구글 계정 환경, 코드가 새면 뚫림)를 솔직히 알린다.

### 2-2c. 카카오톡으로 대여·반납·예약할 때
- `references/kakao-chatbot.md`를 읽고 그 순서대로 안내한다. 카톡 채널은 school-todo-kakao 것을 같이 쓰고(사용자가 정함), 시트는 따로 둔다.
- 챗봇은 웹앱과 같은 처리 함수(`requestLoanAs_`, `returnLoanAs_`, `cancelLoanAs_`, `cancelMySpaceAs_`, `myRequestsAs_`, `submitRequestAs_`)를 부른다. 챗봇에만 있는 규칙을 따로 만들지 않는다.
- 규칙이나 말 알아듣기를 고치면 `node scripts/test_server.js`, `node scripts/test_chatbot.js`, `node scripts/test_router.mjs`를 모두 돌린다(스킬 폴더에서).
- 중계기 배포·오픈빌더 설정은 운영 중인 스쿨투두 챗봇에 영향을 주므로 사용자가 직접 하거나, 먼저 묻는다.

### 2-3. 학생 대결(듀얼)이 필요할 때
- 시설 신청·3D는 구글 시트 + Apps Script에 두고, 실시간 대결만 Supabase로 따로 만든다(`assets/duel_supabase/`). Apps Script는 실시간 통신이 없어 폴링(2~4초)이라 빠른 턴 교환에 맞지 않는다.
- 설치는 README 순서대로. 안내할 때 반드시 말해 줄 것: 익명 로그인 켜기, 무료 플랜은 7일 미사용 시 정지, 학교 와이파이에서 같은 IP의 익명 로그인 시간당 횟수 제한, `service_role` 키 금지, 외부 클라우드에 학생 기록을 두는 것에 대한 학교 규정 확인.
- 판정은 전부 SQL 함수가 한다. 화면에서 점수·정답을 계산하는 코드를 추가하지 않는다. 문제의 정답 열은 학생에게 전달되지 않게 유지하고, 새 함수를 추가하면 `revoke execute … from public` 뒤 필요한 것만 `grant`한다.
- 서버 규칙을 바꾸면 `supabase/test_schema.py`로 로컬 PostgreSQL에서 먼저 시험한다. 실제 Supabase에는 접속할 수 없는 환경이면 그렇게 말하고, 실시간 알림·익명 로그인은 사용자가 확인해야 한다고 알린다.

### 2-4. 3D 프린터 모형이 필요할 때
- `python scripts/make_stl.py --config my_config.json --out stl_out --scale 200 --bed 210`. 프린터 출력 크기를 먼저 묻고, 모르면 220×220mm 기준으로 시작한다. 결과의 닫힌 입체 여부·크기·핀/홈 개수를 확인하고 단면 이미지를 그려 눈으로 점검한 뒤 전달한다. 슬라이서 출력 시험은 이 환경에서 못 하므로 사용자가 해야 한다고 알린다.

### 3. 3D 웹앱 전달
`Code.gs`, `Index.html`은 그대로 전달하면 된다(시트 이름이 설정·배치·사용신청·기물대장으로 같아야 한다). 배포 순서와 접근 코드 설정은 `references/design-notes.md`의 배포 체크리스트를 따라 안내한다.

### 4. 미리보기 보여 주기 (선택이지만 권장)
사용자가 3D를 직접 보고 싶어 하면 미리보기를 만들어 게시한다.
```bash
python scripts/make_preview.py --index assets/apps_script/Index.html --config my_config.json --date <오늘 날짜> --out preview.html
```
대화 안의 게시 페이지는 구글 시트를 읽을 수 없으므로 실제 데이터 연동은 Apps Script 배포 후에만 된다는 점을 분명히 말한다. 브라우저가 없는 환경이면 렌더링을 직접 확인하지 못했다고 솔직히 알린다.

## 지켜야 할 설계 원칙 (이유 포함)
- **설정 시트가 유일한 원천**이다. 공간·교시·분류 이름은 설정에서만 바꾸게 해야 드롭다운, 현황표, 3D가 함께 바뀐다. 이름을 바꿀 때는 기존 기록도 같이 고쳐야 한다고 안내한다.
- **입력과 보기를 분리**한다. 선생님은 3D/신청 화면만 쓰고, 시트 편집 권한은 관리자만 갖는다. 비전문가가 대장을 실수로 지우는 사고를 막는 핵심이다.
- **수식으로 연결하고 배열 수식은 피한다**(`INDEX/MATCH` + 키 열). 엑셀·구글 시트·LibreOffice에서 결과가 같고 고장이 적다.
- **물건 위치는 '최초 보관 장소' + '이동 이력'**으로 관리한다. 위치를 직접 덮어쓰면 이력이 사라진다. 이동 기록은 날짜순으로 아래에 이어 적게 한다.
- **3D가 낯선 사용자를 위한 대체 화면**(표로 보기)과 화면 내 범례·안내를 반드시 유지한다.
- **개인정보 최소화**: 교사 이름과 용도 정도만 두고 학생 정보는 넣지 않는다. 개인 계정 환경에서는 접근 코드가 '아는 사람만 쓰는' 수준의 보호임을 솔직히 설명한다.

## 자주 걸리는 지점
- 사용신청에는 수식이 미리 들어 있다. 코드에서 행을 추가할 때 `appendRow`를 쓰면 수식 행 아래로 밀려 버리므로, 첫 빈 행의 입력 열에만 값을 쓴다(Code.gs가 이미 그렇게 한다).
- 개인 계정에서 '나로 실행' 배포는 사용자 이메일을 알 수 없다. 이메일 허용 목록을 약속하지 않는다.
- 배포 후 코드를 고치면 '배포 관리'에서 새 버전으로 다시 배포해야 반영된다.
- 3D 조작은 사용자가 정한 대로 맞춘다: 이 프로젝트는 '왼쪽 드래그 = 이동, 오른쪽 드래그 = 회전'. OrbitControls 기본값(왼쪽=회전, 오른쪽=이동)을 그대로 쓰지 말고, 화면 버튼·단축키·방 찾기·부드러운 시점 이동 같은 조작 편의를 함께 둔다(`references/design-notes.md`의 시점 조작 항목).
- 사용자가 '상자처럼 보인다 / 건물 느낌이 나게'라고 하면 방 블록을 다듬는 데서 멈추지 말고 건물 외관(창문 있는 바깥벽, 지붕, 층 슬래브, 땅·하늘·그림자)과 '외관 ↔ 층 내부' 전환을 넣는다(`references/design-notes.md`의 건물 외관 항목). 이 화면은 게임 엔진이 아니라 웹 3D라서 걸어 다니기·물리 충돌은 별도 요청이 있을 때 추가한다.
- 방이 많으면 3D가 금방 어지러워진다. 웹앱은 층 버튼·건물 외관/층 내부 전환·층별 목록 패널·층별 표를 함께 제공하고, 방은 종류별 색(신청 대상/학급 교실/행정·지원실/기타)으로 구분한다. 신청 대상이 아닌 방도 기본으로 보여 준다('모든 방 보기'를 끄면 집중 보기). 방을 임의로 숨기지 않는다. 사용자가 '어지럽다'고 하면 3D에 정보를 더 얹지 말고 이런 정리 방식부터 확인한다.
- 여러 층을 쓰는 방은 층을 고르면 그 층에서도 보인다. 층 경계가 도면에서 애매한 공간(예: 도서관과 이어진 오픈 계단 공간)은 사용자가 확인한 층 범위를 따르고, 확인되지 않은 것은 추정이라고 알린다.
- 손으로 그린 배치도의 좌표는 개략적이다. 3D는 '대략의 건물 모양'으로 안내하고, 정밀한 평면도처럼 약속하지 않는다.
