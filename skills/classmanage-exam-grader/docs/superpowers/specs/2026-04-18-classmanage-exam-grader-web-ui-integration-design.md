# classmanage-exam-grader Web UI Integration Design

## 목적

`classmanage-exam-grader`를 웹 UI 중심의 로컬 교사용 채점 워크스테이션으로 재편한다.
새로 만든 `exam-feedback-studio`의 강점인 디자인과 검토 흐름은 이식하되,
기존 `classmanage-exam-grader`의 OCR, 답안 파싱, 채점, 분석 병합, PDF 주석 엔진은 최대한 보존한다.

이 설계의 핵심 원칙은 다음과 같다.

- 기존 엔진을 버리지 않는다.
- 웹은 기본 진입점이 되지만 CLI도 보조 진입점으로 유지한다.
- 교사 검토와 최종 PDF 확정 흐름을 중심으로 재구성한다.
- 배치 단위 폴더 구조를 도입해 여러 작업을 안전하게 병행할 수 있게 한다.

## 배경 문제

현재 `exam-feedback-studio` 작업본은 디자인과 교사 검토 UX는 좋지만,
실제 채점 파이프라인을 별도 앱 안에서 단순화해 다시 만든 부분이 있다.
그 결과 기존 `classmanage-exam-grader`의 자산을 충분히 활용하지 못했고,
전체적으로 "기존 것을 무시하고 다시 만든" 인상이 생겼다.

반대로 `classmanage-exam-grader`는 실제 작업 가능한 엔진을 갖고 있지만,
웹 중심 검토 경험과 배치 관리 화면은 부족하다.

이번 통합은 이 둘을 합쳐 다음 상태를 만드는 것을 목표로 한다.

- 디자인과 검토 화면은 새 작업본의 장점을 살린다.
- 실제 처리 엔진은 기존 `classmanage-exam-grader`를 중심으로 둔다.
- 장기적으로는 하나의 프로젝트 안에서 이해 가능한 구조로 정리한다.

## 목표

- `classmanage-exam-grader` 내부에 웹 앱을 추가한다.
- 웹에서 답안지와 학생 PDF를 업로드하고 배치를 생성할 수 있게 한다.
- 기존 엔진을 호출해 OCR, 답안 파싱, 자동 채점, 분석 병합, PDF 생성까지 연결한다.
- 교사가 학생별 문항 피드백을 수정하고 검토 상태를 관리할 수 있게 한다.
- 최종 확정 후 학생별 피드백 PDF를 다운로드할 수 있게 한다.
- 오류가 발생한 경우 배치 화면에서 원인을 확인할 수 있게 한다.

## 비목표

- 실시간 진행률 스트리밍
- 비동기 작업 큐 또는 백그라운드 워커
- 고급 좌표 기반 주석 정확도 개선
- 기존 엔진의 근본적인 채점 알고리즘 재설계
- SaaS 배포나 다중 사용자 인증

## 권장 구조

프로젝트 루트는 여전히 `classmanage-exam-grader`이며, 웹 앱을 하위 폴더로 추가한다.

├── grader.py

├── pdf_annotator.py
├── llm_subjective_grader.py
├── html_reporter.py
├── webapp/
│   ├── __init__.py
│   ├── main.py
│   ├── schemas.py
│   ├── store.py
│   ├── services/

                ├── output/
                ├── _generated/

## 아키텍처

### 1. 웹은 흐름과 상태를 담당한다

`webapp/main.py`는 FastAPI 진입점이 되며 다음 책임을 가진다.

- 홈 화면 렌더링
- 배치 생성 요청 수신
- 학생 제출물 검토 화면 제공
- 교사 수정 저장
- 최종 PDF 다운로드 제공

웹은 사용자 상호작용과 상태 전이를 담당하지만, 채점의 본체는 아니다.

### 2. 기존 엔진은 처리 본체로 남긴다

다음 파일은 최대한 재사용한다.

- `ocr_extractor.py`
- `answer_key_parser.py`
- `grader.py`
- `analysis_merger.py`
- `pdf_annotator.py`
- `llm_subjective_grader.py`

이 모듈들은 웹 앱에서 직접 또는 얇은 어댑터를 통해 호출된다.
가능한 한 기존 데이터 형식과 함수 경계를 유지한다.

### 3. 연결층은 얇게 둔다

`webapp/services/pipeline.py`는 웹과 기존 엔진 사이의 어댑터 역할만 맡는다.

책임은 아래로 제한한다.

- 업로드 파일을 배치 작업 폴더에 저장
- 기존 엔진이 이해할 수 있는 입력 경로 구성
- 기존 엔진 호출
- 기존 채점 결과를 웹 검토 스키마로 변환
- 교사 수정 결과를 최종 PDF 생성 입력으로 변환
- 단계별 예외를 사용자 친화적 메시지로 포장

이 파일은 새 채점 로직을 만들지 않는다.

## 화면 및 사용자 흐름

### 홈 화면

- 답안지 파일 1개와 학생 파일 여러 개를 업로드한다.
- 최근 배치 목록과 상태를 본다.
- 디자인은 `exam-feedback-studio` 작업본의 템플릿/CSS를 이식한다.

### 배치 상세 화면

- 배치 제목, 학생 수, 검토 필요 학생 수, 최종 확정 수를 본다.
- 검토 우선순위가 높은 학생을 바로 열 수 있다.
- 배치 단위 오류가 있으면 `error.txt` 내용을 표시한다.

### 학생 검토 화면

- 문항별 학생 답안, 정답, 배점, 초안 피드백, 검토 상태를 본다.
- 교사가 피드백 텍스트와 점수를 수정할 수 있다.
- 교사가 검토 상태를 `approved` 또는 `needs_review`로 관리한다.
- 모든 검토가 끝나면 최종 PDF를 생성하고 배치 화면으로 돌아간다.

### 최종 출력

- 학생별 피드백 PDF를 생성한다.
- 생성된 PDF는 배치 상세 화면 또는 학생별 화면에서 다운로드할 수 있다.

## 데이터 모델

웹 쪽에서는 새 작업본의 데이터 모델을 유지하되, 기존 엔진 결과를 여기에 맞춰 변환한다.

- `AnswerKey`
- `StudentAnswer`
- `ReviewItem`
- `ReviewedSubmission`

SQLite는 웹 UI 운영 상태를 저장하는 용도다.

- 배치 메타데이터
- 제출물 상태
- 검토 필요 개수
- 검토용 JSON payload 경로
- 원본 PDF 경로
- 최종 PDF 경로

실제 채점 세부 내용은 배치 폴더의 JSON payload에 저장하고,
SQLite에는 조회와 화면 렌더링에 필요한 최소 메타데이터만 둔다.

## 배치 데이터 흐름

### 1. 업로드

- 답안지 PDF 또는 JSON을 `inputs/`에 저장한다.
- 학생 PDF 또는 테스트용 JSON을 `inputs/`에 저장한다.

### 2. 파싱

- 답안지는 기존 `answer_key_parser.py` 또는 JSON 로더로 파싱한다.
- 학생 제출물은 기존 `ocr_extractor.py` 기반 흐름 또는 JSON 로더로 파싱한다.

### 3. 채점

- 기존 `grader.py`를 사용해 자동 채점을 수행한다.
- 필요 시 `llm_subjective_grader.py`와 `analysis_merger.py`를 연결할 수 있게 설계한다.

### 4. 웹 검토용 변환

- 기존 채점 결과를 `ReviewedSubmission` 형태로 변환한다.
- 변환 결과는 `reviewed/` 아래 JSON으로 저장한다.
- 제출물 상태는 `approved`, `needs_review`, `finalized`, `failed` 중 하나로 관리한다.

### 5. 교사 수정 저장

- 교사의 피드백 수정, 점수 수정, 상태 수정을 JSON payload와 SQLite에 반영한다.

### 6. 최종 PDF 생성

- 교사 수정 결과를 기준으로 `pdf_annotator.py`를 호출한다.
- 결과 PDF는 `output/`에 저장하고 다운로드 가능하게 한다.

## 기존 코드와의 통합 원칙

### 유지할 것

- CLI 진입점 `grade_exam.py`
- 기존 파일 기반 파이프라인 감각
- 기존 테스트 자산
- 기존 프롬프트 및 스키마 구조

### 이식할 것

- 새 작업본의 `templates/*.html`
- 새 작업본의 `static/styles.css`
- 배치/학생 검토 중심 UI 흐름
- SQLite 기반 간단한 웹 상태 저장 구조

### 새로 만들 것

- 기존 엔진을 호출하는 웹 어댑터
- 기존 결과 형식을 웹 검토 모델로 바꾸는 변환층
- 배치 단위 작업 폴더 규약

### 피할 것

- 기존 엔진과 중복되는 새 채점 서비스 재구현
- 새 프로젝트를 별도 애플리케이션으로 계속 분리 유지하는 구조
- 웹 로직 안에 직접 채점 알고리즘을 복사하는 방식

## 오류 처리

오류는 조용히 삼키지 않고 배치 또는 제출물 단위로 드러낸다.

### 배치 단위 오류

대상 예시:

- Gemini CLI 미설치
- 답안지 파싱 실패
- 공통 설정 오류
- 전체 배치에 영향을 주는 파일 구조 문제

처리 방식:

- 배치 상태를 `failed`로 기록한다.
- 배치 폴더의 `error.txt`에 메시지를 저장한다.
- 배치 상세 화면에서 오류 메시지를 보여준다.

### 제출물 단위 오류

대상 예시:

- 특정 학생 PDF OCR 실패
- 특정 학생 채점 결과 생성 실패
- 특정 학생 PDF 확정 실패

처리 방식:

- 가능하면 다른 학생 처리는 계속 진행한다.
- 실패한 제출물만 `failed` 상태로 표시한다.
- 배치 상세 화면에서 실패 제출물을 식별 가능하게 한다.

## 테스트 전략

기존 엔진 테스트는 유지하고, 웹 통합 테스트를 추가한다.

필수 웹 테스트는 다음과 같다.

1. JSON 업로드로 배치 생성이 되는지
2. 기존 엔진 또는 어댑터 결과가 검토 화면에 보이는지
3. 교사 피드백 수정이 저장되는지
4. 최종 PDF가 생성되고 다운로드 가능한지
5. OCR/파싱 실패 시 오류 메시지가 배치 화면에 노출되는지
6. SQLite 스키마 초기화 및 마이그레이션이 안전하게 동작하는지

테스트에서는 PDF와 Gemini CLI 의존성을 줄이기 위해 JSON 입력 경로를 적극 활용한다.

## 마이그레이션 순서

### 단계 1. UI 자산 이식

- `webapp/templates/`와 `webapp/static/styles.css`를 추가한다.
- 홈, 배치 상세, 학생 검토 화면이 더미 데이터로라도 뜨게 만든다.

### 단계 2. 상태 저장 뼈대 연결

- `webapp/store.py`와 `webapp/schemas.py`를 추가한다.
- 배치/제출물/검토 payload 저장 구조를 마련한다.

### 단계 3. 기존 엔진 연동

- `webapp/services/pipeline.py`를 추가한다.
- 새 작업본의 단순 서비스 대신 기존 `answer_key_parser.py`, `grader.py`, `pdf_annotator.py` 등으로 연결한다.
- JSON 업로드 기반 테스트부터 통과시킨다.

### 단계 4. 오류 처리 보강

- 배치 실패와 제출물 실패를 구분해 기록한다.
- 화면에서 원인 노출을 확인한다.

### 단계 5. 문서와 진입점 정리

- README를 웹 우선 실행 흐름으로 갱신한다.
- CLI는 보조 진입점으로 남긴다.

## 실행 모델

기본 실행 모델은 웹 우선이다.

- 일상 사용자는 웹 UI로 작업한다.
- 기존 `grade_exam.py`는 디버깅, 배치 처리, 기존 사용자의 호환성을 위해 유지한다.

README에는 웹 실행 방법을 먼저 안내하고,
CLI는 고급 또는 보조 사용 흐름으로 분리해 설명한다.

## 성공 기준

아래 조건이 충족되면 이번 통합을 성공으로 본다.

- `classmanage-exam-grader` 하나만으로 웹 UI를 실행할 수 있다.
- 새 프로젝트 디자인이 `classmanage-exam-grader` 안에서 자연스럽게 동작한다.
- 기존 엔진 호출이 실제 웹 흐름에 연결된다.
- 교사 검토 후 학생별 PDF를 생성할 수 있다.
- 실패 원인이 배치 또는 제출물 수준에서 드러난다.
- 새 프로젝트를 유지하지 않아도 되는 수준으로 구조가 통합된다.
